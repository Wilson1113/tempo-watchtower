### C1 — Ironwood Receipts (shielded proof-of-payment for Zcash)
- **Niche user**: Small Zcash-shielded merchants/payment processors (CipherPay, ZGo, BTCPay-Server-with-Zcash-plugin operators), exchanges doing shielded withdrawals, and ZEC-paid freelancers/small businesses — the exact personas ZecHub's own "Freelance Privacy Setup," "Accept Payments As A Merchant," and "Keeping Records With Shielded ZEC" guides target. Likely low thousands of active operators; they gather on forum.zcashcommunity.com, the ZecHub Discord/Substack, and r/zcash.
- **Problem (concrete, current)**: ZIP 311 ("Zcash Payment Disclosures") has been **Draft since 2020**, is **Sapling-only**, and explicitly lists Orchard support as unfinished, with **"Reference implementation: TBD."** Since Ironwood (2026-07-28) sealed Orchard and is now the only shielded pool receiving new shielded funds, ZIP 311's existing text cannot produce or verify a disclosure for any current shielded transaction. Today a Zcash user proving a specific shielded payment to a merchant, exchange, or accountant has exactly two options: hand over a full viewing key (massive over-disclosure of unrelated history) or nothing at all.
- **Evidence** (all VERIFIED, fetched directly):
  - ZIP 311 raw spec (zips.z.cash/zip-0311 → github.com/zcash/zips/zips/zip-0311.rst): `"TODO: Add support for Orchard."`; `"Reference implementation: TBD"`; Status line: `"Status: Draft"`.
  - github.com/zcash/zips issues/387 (opened by daira, 2020-08-03): still open, tracking milestone "Selective disclosure."
  - ZecHub `Zcash_Tech/Payment_Disclosures.md` (PR #2090, merged 2026-09-20): `"No current wallet is identified here as implementing ZIP 311 payment-disclosure creation or verification."` and `"[ZIP 311] is still a Draft. Its current text leaves Orchard support, transparent-input support, encoding, versioning, and user-interface rules unfinished."`
  - github.com/ZcashCommunityGrants/zcashcommunitygrants issues/437 (opened 2026-09-21, "Ready for ZCG Review"): a **$42,000** grant application for a "Selected-Payment Receipts SDK," with milestones spanning **December 2026 – February 2027** — i.e., the community is only now funding this, and delivery lands *after* our hackathon deadline.
  - `orchard` crate CHANGELOG (crates.io max version 0.15.5, updated 2026-08-03; v0.15.0 released 2026-07-09) already ships `IronwoodDomain`, `IronwoodNoteEncryption`, and `Bundle::{recover_output_with_ovk, recover_outputs_with_ovks}` — the exact audited primitives needed to build an output-side disclosure for Ironwood, even though ZIP 311 itself hasn't caught up.
- **Why big players won't do it**: ECC/ZF engineering bandwidth is consumed by Ironwood/NU7 consensus work; ZIP 311 has sat unfinished since 2020; the one funded attempt (grant #437) doesn't ship until after this hackathon.
- **Pure-Rust solution**: `ironwood-receipt` — a CLI/library that composes the already-shipped `orchard`/`zcash_client_backend` primitives to let a sender generate a compact, portable "receipt" proving a specific Ironwood output's recipient, amount, and memo (via OVK-based output recovery, mirroring ZIP 311's Sapling output-disclosure design), plus a verifier binary that independently re-fetches the mined transaction from a lightwalletd/Zebra endpoint and re-derives the same fields. No new cryptography — it fills the Orchard/Ironwood gap ZIP 311 has left open using primitives ZF has already published and audited.
- **14-day solo MVP + demo**: Days 1-4: wire up tx-by-txid fetch + OVK-based output recovery against a real Ironwood testnet/mainnet tx. Days 5-8: receipt encoding (txid + output index + recovery proof material) and a verifier that checks recovered fields against a claimed (address, amount, memo) plus chain height/confirmations. Days 9-11: CLI polish, a toy "merchant" and "customer" flow. Days 12-14: demo script/video. **Demo**: send a real shielded ZEC payment to a demo merchant address; the "customer" runs `ironwood-receipt prove`; the "merchant" runs `ironwood-receipt verify` against live chain data and gets "CONFIRMED: 0.5 ZEC to `<addr>`, memo 'Invoice #4821', 12 confirmations" — contrasted on-camera with the only current alternative (handing over a full viewing key).
- **Track fit**: Zcash.
- **Preliminary competitor scan**: Searched GitHub for "zcash+payment+disclosure", "zcash+proof+of+payment", "zcash+receipt" — near-zero relevant hits, nothing targeting Orchard/Ironwood. Closest existing things: Zkool/Zallet/Zingo PC can *view* your own decrypted history in-app but produce no portable, third-party-verifiable disclosure; none advertise ZIP 311 support (confirmed explicitly by the ZecHub guide's own comparison table). The one funded competitor (grant #437) ships after our deadline.
- **Business model sketch**: Open-source CLI/crate (MIT/Apache) to build trust and adoption; a hosted verification-as-a-service API priced per call for exchanges/processors wiring receipts into withdrawal/checkout flows; paid integration consulting for wallets (Zashi/Zodl, ZGo, CipherPay) wanting a "Prove payment" button.

### C2 — HL Clear-Sign (independent verifier for HyperCore multisig actions)
- **Niche user**: Solo/small HyperCore multisig operators — HIP-3 market deployers (500k HYPE / ~$25M stake; a small named set including TradeXYZ and Felix per public coverage), Hyperliquid validators using multisig for validator operations (Pier Two's own published use case), and small trading-team/DAO treasuries on Hypersig or raw native multisig. They gather on the Hyperliquid Discord, the HL docs GitHub, and around Pier Two/Hypersig.
- **Problem (concrete, current)**: Every HyperCore multisig signature — a `withdraw3`, a `usdSend`, a `convertToMultiSigUser` reconfiguration, a `perpDeploy::setOracle` — reduces to signing an EIP-712 `Agent{source, connectionId}` where `connectionId = keccak256(msgpack(action) || nonce || vaultFlag[...])`, and the multisig wrapper (`SendMultiSig{multiSigActionHash, nonce}`) is itself just another opaque bytes32. A hardware wallet cannot render this. Per an independent 2026 hardware-wallet guide: "Ledger has shipped clear-signing support for specific EIP-712 schemas, but the coverage is incomplete, and Hyperliquid's schemas are not guaranteed to be among them on your firmware version" — leaving blind signing as the practical fallback, exactly the failure mode implicated in the Bybit Feb-2025 hack.
- **Evidence** (all VERIFIED, fetched directly):
  - `hyperliquid-python-sdk/hyperliquid/utils/signing.py` (raw source, fetched): `MULTI_SIG_ENVELOPE_SIGN_TYPES = [{"name":"hyperliquidChain",...},{"name":"multiSigActionHash","type":"bytes32"},{"name":"nonce","type":"uint64"}]`; `action_hash()` computes `keccak(msgpack.packb(action) + nonce_bytes + vault_flag[+addr][+expiry])`; `construct_phantom_agent()` returns `{"source": "a"/"b", "connectionId": hash}` — the entire signed content for an L1 action.
  - hyperliquidguide.com "Best Hardware Wallet for Hyperliquid" (fetched, dated 2026-09-23): `"Blind signing is exactly what it sounds like: approving something you cannot read... If you have to enable blind signing, verify the chain ID and the contract address in your software wallet before approving."`
  - frameworks.securityalliance.org signing-verification page (fetched): covers Safe (EVM) and Squads (Solana) with named tooling for both; **no mention of Hyperliquid/HyperCore anywhere**.
  - Official `hyperliquid-dex/hyperliquid-rust-sdk` (GitHub API + raw source grep, fetched): zero occurrences of `multi_sig`/`MultiSig` in `exchange_client.rs` or signing code; repo last pushed 2025-10-21 — the maintained Rust SDK has **no multisig support at all**.
  - GitHub search "hyperliquid+multisig" / "hyperliquid+multi-sig" (fetched via API): only 4 total repos found — `tradingstrategy-ai/open-multisig-hl` (Svelte signer UI, wallet-connect based, no independent decode beyond what MetaMask/Rabby show), `tholos-inc/hyperliquid-multisig-cli` (Python, 1 star, last commit 2025-03-09), `Pier-Two/hyperliquid-multi-sig-actions` (Python, WIP validator-ops scripts, "Use at your own risk"). None independently recompute and cross-check the action hash against a decoded, human-readable action.
- **Why big players won't do it**: Hyperliquid Labs ships the protocol primitive, not signer-side verification UX (explicitly left to ecosystem builders); Ledger/Trezor prioritize broad EVM-schema coverage, not one L1's bespoke msgpack+keccak action-hash scheme; existing ecosystem tools (Hypersig, Pier Two) build signing *convenience*, not independent *verification*.
- **Pure-Rust solution**: `hl-clearsign` — a Rust crate + CLI (optionally served via a tiny local `axum` UI, still a Rust binary) that: (1) decodes every HyperCore action type (`order`, `withdraw3`, `usdSend`, `convertToMultiSigUser`, `perpDeploy`, `spotDeploy`, etc., matching the SDK's ~15 action types) into a human-readable summary with risk flags (e.g., "withdraw3: 50,000 USDC to `0xNEW...` — not in prior withdrawal history"); (2) independently recomputes `action_hash`/`connectionId`/`multiSigActionHash` from the decoded fields using only audited primitives (`rmp-serde` for msgpack, `sha3`/`tiny-keccak` for keccak256, `alloy`/`k256` for EIP-712 hashing); (3) flags any mismatch between that recomputed hash and the hash a signer's hardware wallet is about to show — closing exactly the SEAL-documented Safe/Squads gap for a chain SEAL doesn't cover at all.
- **14-day solo MVP + demo**: Days 1-3: implement and validate action-hash recomputation against recorded real testnet/mainnet multisig transactions. Days 4-8: build the action decoder table with risk flags. Days 9-11: CLI + an offline signer flow (coordinator exports action JSON → each signer runs `hl-clearsign verify` → sees decoded summary + the exact hash to compare on their Ledger). Days 12-14: demo/video. **Demo**: a coordinator silently swaps a withdrawal destination address after other signers "reviewed" it in a group chat; `hl-clearsign` decodes the actual signed bytes live on camera and flags the new, unrecognized address — directly echoing the Bybit-hack narrative from the brief.
- **Track fit**: Hyperliquid (HyperCore).
- **Preliminary competitor scan**: GitHub API search "hyperliquid+multisig"/"hyperliquid+multi-sig" (4 total repos, all reviewed above — none Rust, none independently verify); Hypersig (hosted SaaS, docs reviewed — no published open-source decoder or independent-verification claims); Squads' own Colosseum-blogged tools (multisig-cli/verifier/monitor) prove the *pattern* works and is judge-legible, but exist only for Solana, not HyperCore.
- **Business model sketch**: Open-source core (free CLI/crate, drives trust); paid hosted/self-hosted multi-signer coordination with audit logging and Slack/Telegram alerts on anomalous decoded actions, priced per seat for HIP-3 deployers and trading desks; paid custom-decoder support for bespoke HIP-3 market action patterns.
- **Scores (1-5)**: Evidence 5 / Niche 4 / Big-co neglect 4 / Solo feasibility 5 / Demo-ability 5 / Judging fit 4 / Whitespace 4 → **Total 31**

### C3 — qsk-vault (FROST post-quantum key-material backup for Zcash)
- **Niche user**: The small set of teams currently building FROST-based Zcash shielded custody (`zec-multisig`, "Quorum," and similar threshold-custody operators; Zkool's FROST-DKG users) — builders/operators of shielded multisig treasuries, not end consumers.
- **Problem (concrete, current)**: ZIP 2005 ("Ironwood Quantum Recoverability," Status: Proposed) requires every FROST participant to independently retain `qsk = H^qsk(sk)`, warning explicitly that this material is `"held by every participant"` and that losing it "would" (per the spec) forfeit post-quantum recoverability, while a quantum adversary who obtains it alone could steal funds. Forum thread 56660 (2026-07-13, aryaethn, with replies from ZF's conradoplg and Zkool's hanh) records the ecosystem's own assessment that there is **no standard for backing up this FROST key material**, and that Ironwood-specific FROST tooling work is "not worth being part of a grant proposal" right now — an explicitly acknowledged, unfunded gap.
- **Evidence**: ZIP 2005 raw spec (VERIFIED, fetched) — `"Each participant MUST treat qsk as a secret held at least as securely and reliably as ask."`; `"a quantum adversary may be able to steal the funds with only access to qsk, which is held by every participant."` Forum thread 56660 summary (VERIFIED via WebFetch) — gaps cited: "No standard for backing up additional FROST key material (qsk)"; "Missing DKG interoperability specification." ZCG rejected aryaethn's related proposal on 2026-08-05 (VERIFIED).
- **Why big players won't do it**: ZF/ECC bandwidth is consumed by Ironwood/NU7 consensus and the not-yet-built quantum-resilient Recovery Protocol itself; qsk backup is explicitly a "wallet ops" concern ZF has told applicants isn't currently grant-priority.
- **Pure-Rust solution**: a crate/CLI, `qsk-vault`, that derives `qsk` per ZIP 2005's `H^qsk(sk)` construction (composing `orchard`/`zip32` primitives) and Shamir-splits it (via an existing audited secret-sharing crate) across each FROST participant's own guardians, so no single device compromise or participant loss endangers future post-quantum recoverability — without needing the not-yet-existing Recovery Protocol itself to exist yet.
- **14-day solo MVP + demo**: qsk derivation (Days 1-4, **feasibility risk**: I could not verify, within this research, that the `orchard` crate yet exposes a public `qsk`-derivation function — only Ironwood note-plaintext *versioning* per ZIP 2005 is confirmed shipped; the MVP may need to implement the ZIP's hash construction directly, composing an audited hash primitive rather than a full new signature scheme — UNVERIFIED whether this is a one-day or four-day task); Shamir-split backup/reconstruction CLI (Days 5-9); FROST DKG integration via `frost-core`/`reddsa` (Days 10-12); demo/video (Days 13-14). **Demo**: run a 2-of-3 FROST DKG, split each participant's qsk into guardian shares, simulate losing one participant's device, and reconstruct their qsk share from guardians.
- **Track fit**: Zcash.
- **Preliminary competitor scan**: No dedicated qsk-backup tool found in targeted GitHub/forum searches (UNVERIFIED absence — search budget was constrained). Closest existing thing: ZIP-32 HD derivation itself already covers qsk backup *for ordinary seed-phrase wallets* (per the ZIP's own note) but explicitly does **not** cover FROST groups or non-HD imported keys — exactly this niche.
- **Business model sketch**: Thin as a standalone business — most likely open-source tooling bundled into custody products (`zec-multisig`, Quorum) rather than sold directly; monetization via integration consulting.
- **Scores (1-5)**: Evidence 4 / Niche 2 / Big-co neglect 4 / Solo feasibility 2 (depends on an unverified crate primitive and a still-"Proposed" spec) / Demo-ability 3 / Judging fit 3 / Whitespace 4 → **Total 22**

### C4 — ct-auditor (threshold ElGamal auditor keys for Token-2022 Confidential Transfers)
- **Niche user**: Compliance/ops teams at small-to-mid stablecoin issuers and licensed money-transmitters piloting Token-2022 Confidential Transfers, who need multi-party control over the mint's auditor decryption key so no single compliance officer (or single compromised laptop) can unilaterally decrypt every user's confidential balance. Gather on Solana Developer Discord, Solana StackExchange, QuickNode/Helius technical forums.
- **Problem (concrete, current)**: Token-2022 Confidential Transfers support an optional single ElGamal `auditorElgamalPubkey` on the mint for regulatory decryption — but I queried Solana mainnet directly and found the two flagship Confidential-Transfer-enabled stablecoins currently have this **unset**: `"confidentialTransferMint": {"auditorElgamalPubkey": null, ...}` on both PYUSD and USDG. No published tooling anywhere splits that single ElGamal secret across multiple custodians; every implementation I found treats it as one keypair held by "the issuer."
- **Evidence**:
  - Direct Solana mainnet RPC query (VERIFIED, `getAccountInfo` via `api.mainnet-beta.solana.com`, 2026-09-2x): mint `2b1kV6DkPAnxd5ixfnxCpjxmKwqjjaYmCZfHsFu24GXo` (PYUSD, name/symbol confirmed via on-chain `tokenMetadata`) and mint `2u1tszSeqZ3qBWF3uNGPFc8TzMk2tdiwknnRMWGWjGWH` (USDG) both return `"auditorElgamalPubkey": null` while having Confidential Transfers and Confidential Transfer Fee Config extensions active.
  - `softseco/confidential-sdk` README (VERIFIED, fetched): exposes `deriveAuditorElgamalKeypair` / `decryptTransferAmountAsAuditor` as a **single-keypair** API; "No threshold auditor keys or key rotation features mentioned."
  - Solana Foundation `solana-developer-platform` PR #1801 (VERIFIED, fetched): `"an optional auditor ElGamal pubkey... the platform never generates auditor keys"` — configured once, externally, no threshold support.
- **Why big players won't do it**: This is a narrow compliance-ops feature on a still-near-zero-usage extension (mainnet ZK-proof-program usage reported at "4 transactions... from a single developer wallet" as of 2026-09-09) — Anza/Solana Labs build the base primitive, not issuer-specific key-custody policy; issuers large enough to care (Paxos, PayPal) build in-house HSM/KMS processes rather than open tooling.
- **Pure-Rust solution**: `ct-auditor` — a crate/CLI generating a Token-2022-compatible ElGamal auditor keypair as a t-of-n threshold key by Shamir-sharing the ElGamal scalar over the same curve Solana's own `solana-zk-sdk`/`curve25519-dalek` already use (composing existing audited primitives — no new curve math), plus a decryption CLI where a confidential-transfer amount is only recoverable once t-of-n compliance officers combine their partial decryption shares (standard, linearly-combinable partial ElGamal decryption).
- **14-day solo MVP + demo**: ElGamal keygen + Shamir-split (Days 1-4); partial-decryption share generation/combination (Days 5-8); CLI + a devnet mint with Confidential Transfers and a threshold auditor key configured (Days 9-11); demo/video (Days 12-14). **Demo**: configure a devnet mint's `auditorElgamalPubkey` to a 2-of-3 threshold key from `ct-auditor`, perform a confidential transfer, show that no single compliance-officer share decrypts the amount but any 2 of 3 combined do.
- **Track fit**: Solana.
- **Preliminary competitor scan**: GitHub search for Token-2022 confidential-transfer tooling surfaced `softseco/confidential-sdk` (single-keypair only) and Solana's own internal PR #1801 (single pubkey, externally supplied). No repo found implementing threshold/multi-party auditor decryption for Solana confidential transfers.
- **Business model sketch**: Open-source crate (adoption/trust) + hosted "compliance key-ceremony as a service" for issuers (guided threshold keygen + share-custody guidance), plus integration consulting for stablecoin issuers/OTC desks wanting a documented "no single point of decryption" policy for regulators.

### C5 — pczt-inspect (clear-signing library for FROST/PCZT Zcash signers)
- **Niche user**: Builders/operators of Zcash shielded threshold-custody systems (the same `zec-multisig`/"Quorum" teams surfaced above, plus hardware-signer implementers) who each currently re-derive their own PCZT output-classification logic from scratch.
- **Problem (concrete, current)**: librustzcash issue #2527 (opened 2026-07-02 by ZF's nuttycom, closed via PR #3042) documents a real signer-side risk: NU6.3/Ironwood restricted bundles contain "fabricated same-address outputs" (dummy zero-value outputs with random, non-decryptable ciphertext) and "deferred-witness spends" (ZIP 374 unwitnessed spends) — a naive signer could wrongly reject safe dummy outputs or wrongly accept a maliciously altered deferred-witness spend. The upstream library fix landed as *documentation*, not a reusable enforcement library, so each custody stack must still implement the classification policy itself.
- **Evidence**: librustzcash issue #2527 and PR #3042 (VERIFIED, fetched) — signers must `"recover nothing from the ciphertext, reads a value of zero, and classifies the output as a tolerable dummy output."` Epic #2529 (VERIFIED, fetched) shows this is an ongoing, multi-part gap ("Client orchestration for pre-signed chains" still listed as unresolved). Two independent September-2026 repos confirm builders are actively working this exact problem piecemeal: `Webghost01-NG/veyrin` (TypeScript, "keyless" PCZT "safety layer," created 2026-09-14, VERIFIED via README — demonstrates only *transparent*-address recipient mutation, via a hosted Zallet RPC) and `Biglup/libzcash-signer` (Rust, air-gapped PCZT *signer* on a Raspberry Pi Zero, created 2026-07-22, VERIFIED via README — signs, does not independently verify/classify).
- **Why big players won't do it**: ZF/ECC ship low-level `pczt`/`orchard` crates and document policy in prose, not as an enforced library; each wallet/custody vendor is left to reimplement classification — the kind of repeated boilerplate a solo dev can consolidate.
- **Pure-Rust solution**: `pczt-inspect` — a crate + CLI wrapping `pczt`/`orchard`'s already-shipped decode/recover APIs (`decrypt_output_with_ivk`, `recover_output_with_ovk`) to classify every PCZT action (real spend/output, fabricated dummy, or anomaly) and emit a signed-or-refuse verdict any FROST signing loop or hardware signer can call before producing a signature share.
- **14-day solo MVP + demo**: classifier on top of existing decode APIs, covering the #2527/#2529 rules (Days 1-5); multisig-aware anomaly mode (Days 6-9); CLI + integration example into a FROST signing loop (Days 10-12); demo/video (Days 13-14). **Demo**: feed a legitimate Ironwood PCZT with a fabricated dummy output (correctly classified safe), then a tampered PCZT hiding an extra real spend among dummy outputs (correctly flagged before any signature share is produced).
- **Track fit**: Zcash.
- **Preliminary competitor scan**: GitHub API search "pczt+inspect" and "pczt+signer" (2 hits, both reviewed above — `veyrin`, TS/hosted-web-app/transparent-only; `libzcash-signer`, Rust but a *signer* not an independent verifier). Neither is a reusable Rust library with multisig-loop integration or Orchard/Ironwood output classification — but the existence of both (created within weeks of this research) shows the space is getting crowded fast, hurting whitespace.
- **Business model sketch**: Open-source crate (adoption driver) + paid support/customization for custody vendors integrating into production signing pipelines; possible ZF bounty/grant funding given issue #2527's own author flagged this as an ecosystem-wide need.
- **Scores (1-5)**: Evidence 5 / Niche 2 / Big-co neglect 3 / Solo feasibility 4 / Demo-ability 4 / Judging fit 3 / Whitespace 3 → **Total 24**

- Zcash FROST shielded-multisig wallet/custody itself — rejected: already shipped/being built by multiple teams inside this same hackathon window (`zyn-io/zec-multisig`, live mainnet spend 2026-09-21; `Fatihmaull/zcash-multisig` "Quorum," targeting 2026-10-12; `hhanh00/zkool2`, FROST DKG shipped since ~2025).
- Generic Solana confidential-transfer wallet/SDK — rejected: `softseco/confidential-sdk` and Solana's own developer-platform PR #1801 already cover base integration; whitespace is specifically in threshold auditor-key custody (kept as C4), not the base SDK.
- Solana post-quantum "Winternitz vault"-style product — rejected: Blueshift's `solana-winternitz-vault` already shipped this pattern on mainnet (referenced by Colosseum's own blog, live since ~2025); not novel whitespace.
- Wrapped-ZEC (zenZEC) proof-of-reserves — rejected: only marketing-level sources found on Zenrock's MPC custody; no documented user complaint or gap located, so it didn't meet the evidence bar.
- Squads/Safe-style multisig verifier for Solana — rejected: Squads already shipped `multisig-cli`/`multisig-verifier`/`multisig-monitor` (Rust, open-source, referenced in Colosseum's own blog); well-served already.
- Hyperliquid signing *convenience* UI (like `open-multisig-hl`/Hypersig) — rejected as a standalone idea (the harder independent-verification angle was kept as C2 instead): existing tools already provide signing convenience; the underserved slice is independent hash verification, not another signer UI.
