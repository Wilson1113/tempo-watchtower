### A1 — HL-NODE-GUARD (Hyperliquid non-validator self-healing supervisor + data-integrity layer)
- Niche user (who exactly; roughly how many; where they gather): Solo quants / small trading firms / researchers who run their own Hyperliquid **non-validating node** (`hyperliquid-dex/node`) to get L2/L4 book, fills, and order-status data instead of paying $500-1,500/mo for a managed feed. Gather on the `hyperliquid-dex/node` GitHub issues tracker, Hyperliquid Discord, and blogs like hydromancer.xyz/QuickNode. Scale: dozens-to-low-hundreds of self-hosted operators.
- Problem (concrete, current 2025-2026): The reference `hl-node`/`hl-visor` binary has no throughput-aware health check — it stays pinned to a degraded peer (block delivery drops from ~12 blk/s to ~2 blk/s) until manually restarted, and restarting causes a **permanent, unrecoverable gap** in written output because bootstrap only backfills a limited window. Also: unexplained ~10-12 GiB/hour memory leak on binary index 111 forcing restarts every 1.5-9 hours (each restart = another gap); crash loop with "too many blocks to request" panic 6-12x/day; bootstrap loop impossible from some locations (829MB payload, 60s timeout, ~1MB/s peer transfer speed). Node also dumps ~100GB/day of logs with minimal built-in pruning.
- Evidence (>=2 primary-source links; quote the key line; mark VERIFIED/UNVERIFIED):
  - VERIFIED — github.com/hyperliquid-dex/node/issues/156 (opened 2026-07-21): "the stream never timed out because it technically remained alive... fell behind by approximately 0.85 minutes per minute for 48 minutes... After manual restart... created a permanent 28-minute data gap in written output." Fetched directly.
  - VERIFIED — github.com/hyperliquid-dex/node/issues/173 (opened 2026-09-21, author susuper): "hl-node RSS grows ~10-12 GiB/h on binary index 111... `child_low_memory` restart now fires every 1.5-9 h." Fetched directly, no team response as of fetch.
  - VERIFIED — github.com/hyperliquid-dex/node/issues/160 (opened 2026-08-01): panic `"too many blocks to request"` causing 6-12 crashes/day, each with 15-25 min data loss. Fetched directly.
  - VERIFIED — github.com/hyperliquid-dex/node/issues/143 (opened 2026-03-30): "829MB ÷ 60s timeout = ~14 MB/s required. All peers serve at ~1 MB/s... bootstrap is physically impossible from my location." Fetched directly.
  - VERIFIED — quicknode.com/blog/hyperliquid-sentry-peering-explained (2026-08-19): "Root peers rotate, saturate, and disconnect... the occasional block that arrives seconds late... exactly the block a trading system cannot afford to miss." QuickNode sells a $500/mo fix (3 dedicated sentry IPs, ~1.1TB/day mempool).
  - VERIFIED — hydromancer.xyz/resources/how-to-get-hyperliquid-data (2026-07-15): "it's a 24/7 operations commitment: finding peers, staying synced, handling crashes, monitoring... every crash, every network upgrade, every schema change" is a project operators "own... forever."
- Why big players won't do it: Hyperliquid Labs explicitly disclaims responsibility — the companion `order_book_server` repo states it is "a standalone project, not written by the Hyperliquid Labs core team," provided "as is." The paid fixes that exist (QuickNode, Dwellir/Hydromancer "Unlimited Node" at $1,500/mo) are managed-hosting upsells for firms who'd rather not self-host — none ship an open-source daemon that makes *your own* node self-healing. That's a narrow, low-revenue niche a VC-scale infra company has no reason to target.
- Pure-Rust solution (what ships: crate/CLI/daemon/...; the core technical insight): A Rust daemon (`hl-guard`) beside `hl-node` that (1) tails the node's own output streams and computes real-time block-arrival throughput (fixing the exact liveness-only blind spot in #156) to trigger peer rotation via `override_gossip_config.json` before a human has to; (2) on any detected gap, auto-backfills from the requester-pays S3 archive (`s3://hl-mainnet-node-data`) so gaps self-heal instead of becoming permanent; (3) cross-validates local fills/trades against the documented archive quirks (18 cataloged "traps": missing hours, silent 500-row pagination caps, delisted coins still "settling" at zero, etc.) so downstream consumers get a data-quality report instead of silent corruption; (4) exposes Prometheus metrics for the memory-leak pattern in #173 so operators get advance OOM warning. Core insight: pure async I/O / process-supervision (tokio, file-tailing, S3 client, peer-config rewriting) treating `hl-node` as a black box to babysit and repair — no chain logic needed.
- 14-day solo MVP + what a 3-minute demo shows: Days 1-4: tokio tailer for `replica_cmds`/`node_fills_by_block` + throughput-lag detector. Days 5-8: peer-rotation trigger + S3 backfill-on-gap logic. Days 9-11: data-quality checks against known traps + Prometheus exporter. Days 12-14: polish. Demo: run a real non-validator node in a sandboxed/testnet mode, artificially throttle the peer connection (simulating #156), show `hl-guard` detecting the stall within seconds, rotating peers, and the gap auto-closing from S3 — side-by-side against an unmodified node that stays stuck.
- Track fit: Hyperliquid ($100k/10) — directly improves node-operator reliability, a pain the project's own docs disclaim responsibility for.
- Preliminary competitor scan: Searched GitHub (`hyperliquid-dex/node` issues, `purr-build/hyperliquid-node-indexer`, `BuckshotCapital/hyperliquid-node`, `BuckshotCapital/hl-mempool-tap`, `validaoxyz/hyperliquid-exporter`, `dwellir-public/hyperliquid-exporter`), crates.io (~60 `hyperliquid`/`hl-*` crates, all trading/SDK/execution — none about node supervision), and commercial Hydromancer/QuickNode/Dwellir offerings. Closest things: (a) `hyperliquid-exporter` (Go, Prometheus metrics only — observability, no self-healing/backfill); (b) `purr-build/hyperliquid-node-indexer` (Rust, 3 stars, early-stage — does checkpoint-based restart recovery + ClickHouse ingestion, but NOT throughput-aware peer rotation or S3 gap backfill; short 1-day TTLs suggest exploratory, not hardened); (c) `BuckshotCapital/hl-mempool-tap` (Rust, 1 star — a *different* problem, DIY mempool gossip tap, and it self-documents a "15% per-Tx SA gap" limitation, confirming this whole space is hard and unsolved); (d) QuickNode/Dwellir paid peering — solves the peer problem only if you pay and don't self-host. None combine self-healing + gap-backfill + data-quality validation in one open pure-Rust tool.
- Business model sketch: Open-source core (MIT/GPL) + paid hosted dashboard/alerting SaaS tier for firms running 3+ nodes, or a support contract; could sell an "audited node data" attestation feed to downstream consumers who don't want to run their own guard.
- Scores 1-5: Evidence 5 / Niche 4 / Big-co neglect 4 / Solo feasibility 4 / Demo-ability 4 / Judging fit 4 / Whitespace 4 -> **total 29/35**

### A2 — TEMPO-WATCHTOWER (Settlement watchtower for Tempo Machine-Payments-Protocol streaming-session channels)
- Niche user (who exactly; roughly how many; where they gather): Server-side operators (payees) who accept Tempo's MPP "session" intent — i.e., anyone selling metered/streamed services (LLM token streaming, per-request APIs) over HTTP 402 and getting paid via on-chain escrow channels. As of the protocol's own self-reported early metrics: "roughly 31,100 transactions, $3,730 in volume, 671 registered agents, and 326 servers" (late March 2026) — small today, but growing fast as MPP is co-authored by Stripe and Tempo/Paradigm and pushed as the flagship Tempo use case. Gather in the `tempoxyz` GitHub org, `paymentauth.org`/IETF-style spec discussion, and Tempo developer Discord.
- Problem (concrete, current 2025-2026): The Tempo "session" intent (`draft-tempo-session-00`, dated 2026-09-23 — one day old at research time) is a **unidirectional payment channel**: the client can call `requestClose()` on-chain at any time, which starts a hard **15-minute wall-clock grace period**, after which the client can call `withdraw()` and take back *all remaining unsettled funds* — funds the server had already earned by serving the request but hadn't yet settled on-chain. The spec puts the operational burden entirely on the payee: "Servers SHOULD... Monitor for `ChannelClosed` or `CloseRequested` events" and must submit `settle()`/`close()` before the deadline or lose the money — during "network congestion or maintenance windows," exactly when a server is least able to react manually.
- Evidence (>=2 primary-source links; quote the key line; mark VERIFIED/UNVERIFIED):
  - VERIFIED — paymentauth.org/draft-tempo-session-00.txt (dated "23 September 2026," authored by Tempo Labs: L. Horne, G. Konstantopoulos, D. Robinson, B. Ryan, J. Moxey). §13.3 "Forced Close": "1. Client calls requestClose(channelId) on-chain. 2. 15-minute grace period begins... 3. Server can still settle() or close() during grace period. 4. After grace period, client calls withdraw(channelId). 5. Client receives all remaining (unsettled) funds." Fetched and read directly (full text).
  - VERIFIED — same document §14.12 "Chain Reorganization": "servers SHOULD: 1. Re-verify channel state periodically during long-lived sessions. 2. Monitor for ChannelClosed or CloseRequested events. 3. Cease service delivery if the channel becomes invalid." §14.13: the grace period exists to give payees "time to detect close requests and submit final settlements, even during network congestion or maintenance windows" — i.e., the spec itself frames missed settlement as an expected operational failure mode, not an edge case.
  - VERIFIED — formo.so/blog/mpp-machine-payments-protocol-explained (referenced via search, MPP overview) + tempoxyz/mpp-rs GitHub repo (fetched via `api.github.com`, description: "Rust SDK for the Machine Payments Protocol") confirm MPP has an official client/server SDK but this SDK is a protocol library, not an autonomous on-chain monitoring/settlement daemon.
- Why big players won't do it: Tempo Labs' job is to ship the protocol and reference SDKs (mpp-rs, tidx, wallet-rs, zones — all in the `tempoxyz` org), not to run a 24/7 monitoring service for every small payee's channels; that's exactly the kind of "boring ops tooling for a long tail of tiny sellers" a protocol team deprioritizes versus core chain work, especially only one day after the spec itself was published.
- Pure-Rust solution (what ships: crate/CLI/daemon/...; the core technical insight): A Rust daemon/CLI (`tempo-watchtower`) that a payee (or a third party the payee delegates to, Lightning-watchtower-style) runs alongside their API server: it subscribes to `ChannelClosed`/`CloseRequested` events for the payee's channel(s) on Tempo via RPC/websocket, tracks the server's own signed voucher state (per §12 "Server-Side Accounting": `acceptedCumulative`, `spent`, `settledOnChain`), and automatically submits `settle()`/`close()` well before the 15-minute deadline — with a redundant/backup mode so the watchtower itself can run on separate infra from the main API server (protecting exactly against the "maintenance window" scenario the spec calls out). Core technical insight: pure async event-subscription + deadline-driven transaction submission (tokio, an EVM-compatible RPC client since Tempo channels are precompile/EVM-based, a simple persistent ledger of per-channel deadlines) — no new cryptography, just a hardened scheduler that a protocol SDK deliberately leaves out.
- 14-day solo MVP + what a 3-minute demo shows: Days 1-4: EVM event subscriber for the deployed `TempoStreamChannel` contract (`ChannelClosed`/`CloseRequested`). Days 5-8: local accounting ledger mirroring §12's accepted/spent/settled fields + deadline scheduler. Days 9-12: automatic `close()`/`settle()` submission + retry/backoff. Days 13-14: polish. Demo: open a real session channel on Tempo testnet, simulate the payee's main server "crashing" (kill the process), have the client call `requestClose()`, show the countdown, and show `tempo-watchtower` — running independently — submitting `close()` with seconds to spare, next to a control run with no watchtower where the funds are lost to `withdraw()`.
- Track fit: Tempo ($100k/10) — directly hardens the flagship MPP use case Stripe/Tempo are promoting, and composes with the official spec/SDK rather than replacing it.
- Preliminary competitor scan: Searched GitHub API for `tempo+stream+channel+watchtower`, `TempoStreamChannel`, `tempo+channel+keeper`, `mpp+session+settle+bot` (zero results for all) and crates.io for `tempo-stream`/`tempo channel` (only false-positive matches on musical "tempo" — MIDI/audio libraries, nothing payment-related). Listed the full `tempoxyz` GitHub org (50+ repos: `mpp-rs`, `mpp-go`, `mpp-specs`, `tidx`, `wallet-rs`, `zones`, `txgen`, `schelk`, `revm-inspectors`, etc.) — no watchtower/keeper/settlement-monitor repo exists. Closest thing is the general-purpose `mpp-rs` SDK, which gives you the primitives to build this but does not ship the always-on monitoring daemon itself. Whitespace looks clean, though the ecosystem is only ~6 months old and could move fast.
- Business model sketch: SaaS — payees pay a small % of at-risk channel value or a flat monthly fee to have a third party run watchtower coverage for their channels (classic Lightning-watchtower economics), or sell it as self-hosted open-source + paid managed multi-region redundancy.
- Scores 1-5: Evidence 5 / Niche 3 (ecosystem still small — hundreds of servers, not thousands) / Big-co neglect 4 / Solo feasibility 5 / Demo-ability 5 / Judging fit 4 / Whitespace 5 -> **total 31/35**

### A3 — ZLIGHT-PROOF (Verifiable honest-uptime attestation for independent Zcash light-wallet-server operators)
- Niche user (who exactly; roughly how many; where they gather): Independent, mostly unpaid/volunteer operators of Zcash `lightwalletd`/`Zaino` light-client servers who participated in the community's "Zcash Operators: Earn ZEC for your uptime" reward program. ~50-120 named operators (one snapshot: "50 nodes qualified... for a total of 41.7 ZEC" in March 2026; another post: "there used to be 3 nodes and now there are 120 nodes"). Gather at forum.zcashcommunity.com thread 52090, the `zecrocks/hosh` and `alexxiy/nodus` monitoring tools, and Telegram.
- Problem (concrete, current 2025-2026): The reward program that funded these operators **collapsed** in April 2026 specifically because it had no way to detect Sybil gaming — one person ran many nodes to farm rewards, "stealing rewards from dozens of other participants, for many months" — and the maintainer shut the program down, writing "my motivation is frankly crushed." The existing monitoring tool (Hosh, Rust, 6 stars, 19 open issues) only checks liveness/ping — no way to prove a server is (a) a distinct honest operator and (b) actually serving correct chain data, not just answering a health check. A separate forum thread explicitly asks for exactly this primitive and finds no answer.
- Evidence (>=2 primary-source links; quote the key line; mark VERIFIED/UNVERIFIED):
  - VERIFIED — forum.zcashcommunity.com/t/52090 post #329 (2026-04-15, emersonian): "I recently discovered that an individual is gaming the reward system to a large degree. They are running many nodes to farm the rewards, stealing rewards from dozens of other participants, for many months... my motivation is frankly crushed." Fetched via Discourse JSON API.
  - VERIFIED — same thread post #293 (zk_nd3r, 2026-04-04): "The participant list approach has a trust problem, whoever controls nodus.alexxiy.top controls who gets paid... What you actually want is each node proving its own uptime independently." A community member independently proposing almost exactly this primitive.
  - VERIFIED — forum.zcashcommunity.com/t/51811 (pacu, 2025-07-31): "Wallets make quite a parasitic usage of lightwalletd... The incentives of running such infrastructure is not clear for good actors... Bad actors have more incentives [to] run 'Free Email' kind of light client infrastructure (learn about users' IPs and sell that data) than good actors." Fetched directly.
  - VERIFIED — github.com/zecrocks/hosh README (fetched): "Hosh brings awareness to the uptime of light wallet servers" — confirmed liveness/ping-only, 19 open issues, no correctness/Sybil features.
- Why big players won't do it: This is a tiny, unpaid volunteer economy (the whole reward pool was one individual's personal donor budget, ~$15k/month at its peak). No foundation has budget interest in Sybil-resistance tooling for a volunteer side-program — Electric Coin Co/Zcash Foundation are focused on the much bigger Zebra/Zaino/Zallet core-node rewrite.
- Pure-Rust solution (what ships: crate/CLI/daemon/...; the core technical insight): A lightweight Rust daemon operators run beside `lightwalletd`/`zainod` that (1) periodically signs a heartbeat containing the server's current chain tip + a fresh nonce, cross-checked against multiple known-good full nodes, so a heartbeat proves *fresh, correct* state rather than mere reachability; (2) publishes heartbeats in an append-only, independently-verifiable log so no single list-curator is a trusted single point of failure (directly answering zk_nd3r's critique); (3) ships a CLI verifier any future grant-funder can run to audit a claimed operator list against the signed log. Core insight: pure async networking/crypto-attestation (tokio, ed25519 signing, a light gRPC/HTTP client comparing chain tips across servers) — no protocol changes needed.
- 14-day solo MVP + what a 3-minute demo shows: Days 1-5: heartbeat signer + chain-tip cross-check against 3+ known-good full nodes. Days 6-9: append-only signed log format + CLI verifier. Days 10-12: simple dashboard reusing Hosh's public node list as seed data. Days 13-14: polish. Demo: spin up 3 "honest" lightwalletd instances plus one "Sybil" cluster (5 processes behind one IP claiming to be 5 servers); show the verifier catching the Sybil cluster (correlated/stale chain-tip fingerprints) while confirming the 3 honest ones — directly re-staging the exact failure mode that killed the real program.
- Track fit: Zcash ($100k/10) — infrastructure for the light-client ecosystem the Foundation is actively investing in; composes with Zaino/lightwalletd rather than replacing them.
- Preliminary competitor scan: Searched GitHub (`zecrocks/hosh`), forum.zcashcommunity.com grant applications (found "Auto-Failover SDK for Zcash lightwalletd," rejected by ZCG 2025-11-10 — that solves *client-side failover/routing*, a different problem from *operator honesty attestation*). **Important flag:** fetched frontiercompute.cash (operator "zk_nd3r" — the same forum user who proposed this exact primitive) and found they already run a live, adjacent product line under "Frontier Compute": `ZAP1`/"attest" ("Typed claims, BLAKE2b Merkle paths, Zcash anchor records, and a standalone verifier... Limit: the receipt does not prove every action it references... A valid Merkle path proves inclusion, nothing more"), plus a Zcash explorer, split-key custody, and an HTTP-402 shielded-payment tool. This is a *generic* attestation primitive (a "ZIP draft / not adopted" proposal), not a purpose-built lightwalletd-uptime-Sybil-resistance product — but it means a capable solo operator is already deeply embedded in exactly this niche, which is a real whitespace risk for anyone else entering it.
- Business model sketch: Likely a public good (grant-funded) rather than a revenue business; could take a cut of any future incentive pool for running verifiable distribution. Weakest business-plan angle of the set.
- Scores 1-5: Evidence 5 / Niche 5 / Big-co neglect 5 / Solo feasibility 4 / Demo-ability 4 / Judging fit 3 (weak business plan) / Whitespace 2 (active adjacent competitor, zk_nd3r/Frontier Compute) -> **total 28/35**

### A4 — HL-COREWRITER-TRACE (Cross-layer tracer for HyperEVM↔HyperCore CoreWriter actions)
- Niche user (who exactly; roughly how many; where they gather): Smart-contract developers building on HyperEVM who call the `CoreWriter` precompile (`0x3333...3333`) to trigger HyperCore actions (spot orders, transfers) — e.g., HIP-3 market builders, bridge/vault integrators. Small (dozens of active teams), gather on `hyperliquid-dex/node` GitHub issues and Hyperliquid dev Discord.
- Problem (concrete, current 2025-2026): CoreWriter actions can succeed on the EVM side (status 1, correct `RawAction` event) while producing **zero effect on HyperCore** — no order, no ledger change — with no error surfaced anywhere and no official team response as of the report. Developers have no way to see *why* an action silently vanished between layers. A related bug: the public `/evm` RPC silently returns *current* state for historical/future block numbers on `eth_call`/`eth_getCode` instead of erroring, corrupting any downstream dataset that trusts the requested block number.
- Evidence (>=2 primary-source links; quote the key line; mark VERIFIED/UNVERIFIED):
  - VERIFIED — github.com/hyperliquid-dex/node/issues/172 (opened 2026-09-21, author wsim101): "CoreWriter (`0x3333...3333`) actions succeed on HyperEVM testnet (tx status 1, `RawAction` event emitted with correct data) but produce no effect on HyperCore whatsoever." Fetched directly; no team response documented.
  - VERIFIED — github.com/hyperliquid-dex/node/issues/158 (opened 2026-07-28): "An explicit unsupported-block error is easy for callers to detect and handle. A valid-looking response from the wrong state is not." Fetched directly.
- Why big players won't do it: Narrow developer-tooling gap for a still-small builder population; the team's own repo disclaimers (see A1) show they lean on the community for tooling around the edges of the core exchange rather than shipping first-party debugging tools for a niche integrator audience.
- Pure-Rust solution (what ships: crate/CLI/daemon/...; the core technical insight): A CLI/daemon that runs a non-validator node in parallel with a HyperEVM RPC client, subscribes to `CoreWriter` `RawAction` events on the EVM side, and cross-references each action against the corresponding `replica_cmds`/`node_order_statuses` stream on HyperCore within the same block window, flagging any EVM-success-but-Core-silent mismatch in real time with the decoded action payload. Core insight: pure async stream-joining across two independently-sourced event streams (EVM logs + L1 replica stream) keyed by block height.
- 14-day solo MVP + what a 3-minute demo shows: Days 1-5: EVM log subscriber for CoreWriter events. Days 6-9: HyperCore replica-stream reader + matching logic. Days 10-12: CLI diff/alert output. Days 13-14: polish. Demo: replay the exact failing transaction from issue #172 (or a testnet reproduction) and show the tool flagging "EVM: success / Core: no matching action found" within seconds, plus a control case where it correctly matches.
- Track fit: Hyperliquid — developer-experience tooling for HyperEVM/HIP-3 builders.
- Preliminary competitor scan: Searched `hyperliquid-dex/node` and `order_book_server` repos/issues; no existing cross-layer tracer found. Risk: if the Hyperliquid team responds to #172 with an official fix or debugging guidance before/during the hackathon, this idea's urgency drops.
- Business model sketch: Weak standalone business — more of a free dev-tool than a company; could fold into a broader "HyperEVM observability" SaaS if scope grows.
- Scores 1-5: Evidence 4 / Niche 3 / Big-co neglect 3 / Solo feasibility 4 / Demo-ability 3 (needs a live/testnet repro) / Judging fit 3 / Whitespace 4 -> **total 24/35**

### A5 — ALPENGLOW-BRIDGE (Compatibility shim for Solana RPC/indexer/dashboard operators migrating off vote-transaction-based metrics)
- Niche user (who exactly; roughly how many; where they gather): Small/solo Solana RPC operators, block-explorer maintainers, and staking-dashboard builders who don't have a dedicated infra team to rewrite their indexing pipeline for Alpenglow. Gather on Solana validator Discord/forums and Substack validator-discussion digests (chainflowsol).
- Problem (concrete, current 2025-2026): Alpenglow removes vote transactions from the block ledger entirely (historically ~59% of all Solana transactions) and silently changes the *units* of the `epoch-credits` field from vote-counts to reward-lamports at the migration boundary — "a silent unit change that every staking dashboard will have to handle." `vote-account --output json` also breaks backward compatibility.
- Evidence (>=2 primary-source links; quote the key line; mark VERIFIED/UNVERIFIED):
  - VERIFIED — xroot.dev/blog/alpenglow-vote-rewards-leader-split (2026-09-17): "A silent unit change that every staking dashboard will have to handle... Until dashboards catch up, read reward lamports from the vote account directly." Fetched directly.
  - VERIFIED — solanacompass.com Alpenglow infrastructure article (updated 2026-09-21): "Indexing changes are required for Alpenglow... Vote transactions disappearing from blocks will change both historical and real-time transaction counts in ways that affect any tooling relying on raw ledger data." Fetched directly.
- Why big players won't do it: **Unclear — likely they already are.** TODO/flag: Triton, Helius, and QuickNode all publish their own Alpenglow migration blog posts already (found via search), meaning majors are actively covering this territory with documentation, even if not with a packaged open-source shim. This weakens the "big-co neglect" case relative to the other candidates.
- Pure-Rust solution (what ships: crate/CLI/daemon/...; the core technical insight): A small Rust compatibility crate/sidecar that sits between raw RPC/Geyser output and a legacy indexer, translating post-Alpenglow shapes (missing vote txs, reunited epoch-credits units) back into the pre-Alpenglow shape small indexers were already built against, buying migration time without a full rewrite.
- 14-day solo MVP + what a 3-minute demo shows: A shim daemon fed real Alpenglow testnet data, shown producing schema-stable output that an unmodified legacy dashboard can keep consuming, versus the same dashboard breaking/showing nonsense numbers when fed raw post-Alpenglow data directly.
- Track fit: Solana ($100k/10).
- Preliminary competitor scan: Confirmed via search that Triton/Helius/QuickNode have migration *documentation*; did not find a shipped open-source compatibility *shim* (a gap between "docs exist" and "code exists" that could still be whitespace) — but this needs more verification than time allowed.
- Business model sketch: Thin — likely valuable only for the weeks around the actual mainnet cutover, and that cutover date is itself unresolved (see below), which undermines a durable business.
- Scores 1-5: Evidence 4 / Niche 3 / Big-co neglect 2 / Solo feasibility 4 / Demo-ability 3 / Judging fit 3 / Whitespace 2 -> **total 21/35**
- **Timing risk flag:** Sources conflict on the mainnet activation date. One article's headline claimed "Sep 28," but a more careful, later-dated (2026-09-21) article explicitly corrected that: "No mainnet activation date has been announced." Triton's own Agave 4.3 writeup (updated 2026-09-18) states Alpenglow "does NOT activate with 4.3... expected around the 4.4 release." A hackathon bet on an unscheduled migration event is risky — this is the weakest candidate of the five and is not recommended.

## Ranked top 3

1. **A2 — TEMPO-WATCHTOWER** (31/35). Best combination of rock-solid, extremely fresh primary evidence (the spec document is dated one day before this research), confirmed clean whitespace, a crisp 14-day scope, and a demo that visually proves the problem and the fix in under 3 minutes (money saved vs. money lost). Main risk is that the MPP ecosystem is still small (hundreds of servers), so "Potential Impact" TAM framing needs care in the pitch — but it composes directly with a flagship Stripe/Tempo/Paradigm product, which should help Judging fit (Novelty, Composability).

2. **A1 — HL-NODE-GUARD** (29/35). The strongest evidence base of the set (four separate, dated, currently-open GitHub issues on the exact repo Hyperliquid tells operators to run), a well-understood user (self-hosting quants), and a very legible demo (throttle a peer, watch it self-heal). Slightly more crowded adjacent space (paid managed alternatives exist) than A2, but nothing free/open does what this does.

3. **A3 — ZLIGHT-PROOF** (28/35). Extremely strong niche-specificity and "big-co neglect" story (a volunteer reward program that literally collapsed from lack of exactly this tooling, in the operators' own words), and a good small-scope MVP — but downgraded below A1/A2 because of the confirmed active competitor (zk_nd3r/Frontier Compute) working in immediately adjacent territory, and the weakest Business Plan angle of the set (Judging criterion (f)), which the hackathon rubric explicitly scores.

## Rejected ideas (one-liner each)
- Ethereum blob archival beyond the 18-day PeerDAS retention window — rejected: already shipped and live by BlobArchive.net/`bloar` (open source, Apache-2.0, actively seeking a second operator, not a hackathon-fillable gap).
- HIP-3 oracle/mark-price relayer infra for Hyperliquid builder-deployed perps — rejected: already served by Pyth's "HIP-3 as a Service" managed relayer and RedStone's "HyperStone" three-tier oracle network; and the market itself is tiny (trade.xyz alone is >90% of HIP-3 open interest; Felix, the first HIP-3 platform, already shut down).
