## Section B — Candidate ideas (6)

### H1 — corewriter-receipts
- **Niche user:** Rust/Solidity developers building HyperEVM contracts that call CoreWriter to act on HyperCore (lending markets, bridges, RWA issuers, vault managers) — a growing but still small developer set; they gather in the `hyperliquid-dex/node` GitHub repo and Hyperliquid dev Discord.
- **Problem (current, 2025-2026):** CoreWriter is "only an event emitter" — the HyperEVM transaction reports success (`status 1`, `RawAction` event emitted) even when the corresponding HyperCore-side action is rejected, delisted, under-margined, or otherwise fails. There is no error, no revert, no trace. A developer testing this in September 2026 methodically ruled out encoding, notional, slippage, and account-specific causes and still saw "no `userFills` entry, no `userNonFundingLedgerUpdates` entry, no balance change, no open order, no error of any kind."
- **Evidence:** (1) VERIFIED — hyperliquid-dex/node issue #172, opened 2026-09-21, https://github.com/hyperliquid-dex/node/issues/172 — quote above. (2) VERIFIED — hyperliquid-dex/node README, https://github.com/hyperliquid-dex/node — confirms the raw building blocks exist but are not wired together: `--write-system-and-core-writer-actions` writes "CoreWriter and HyperCore to HyperEVM transfer data indexed by HyperEVM tx hash," and `--replica-cmds-style actions-and-responses` can log both the action and its response, but nothing in the stack correlates the two into a developer-facing outcome.
- **Why big players won't do it:** Hyperliquid Labs' design choice is deliberate — CoreWriter intentionally does not revert HyperEVM state on a HyperCore-side failure, by architecture (asynchronous cross-VM execution). Fixing this at the protocol level would be a breaking consensus change; a third-party correlation layer is the only near-term fix, and it serves a developer population too small for Hyperliquid Labs to prioritize internally.
- **Pure-Rust solution:** A Rust daemon that tails hl-node's `system_and_core_writer_actions` and `replica_cmds` (actions-and-responses) output files (or the equivalent public gRPC/API stream), joins each HyperEVM tx hash to its eventual HyperCore-side outcome (fill / no-fill / reject / margin failure), and re-exposes it as (a) a queryable Rust library (`corewriter-receipts` crate) any HyperEVM contract's off-chain bot can embed, and (b) a small webhook/gRPC daemon for teams that don't want to run their own node. Core technical insight: the correlation key (HyperEVM tx hash) already exists in the node's own output; nobody has built the join.
- **14-day solo MVP + demo:** Days 1-4: parse `system_and_core_writer_actions` + `replica_cmds` file formats from a testnet non-validator node. Days 5-9: build the join engine + a minimal Rust crate API (`await_outcome(tx_hash) -> Outcome`). Days 10-12: wrap in a small async daemon with a webhook. Days 13-14: polish + demo script. **3-minute demo:** submit a CoreWriter spot order that will be rejected (insufficient margin) on testnet; HyperEVM tx shows `status 1` with no indication of failure; `corewriter-receipts` dashboard flags "REJECTED: insufficient margin" within seconds — directly reproducing and solving issue #172 live.
- **Track fit:** Hyperliquid ($100k/10).
- **Preliminary competitor scan:** GitHub search "hyperliquid corewriter monitor|receipt|outcome" → 3 hits, all Solidity read/write *libraries* (emo-eth/hyperevm-tools, native-markets/hyperevm-tools, 0xkaz/hl-evm-core-playground) — none track outcomes, all closest to "how to call CoreWriter," not "what happened after." crates.io search for "corewriter" → 0 results. Closest existing thing: `hyper-evm-lib`'s local CoreSimulator (Obsidian Audits) — but that's a *test-time* simulator for Foundry, not a production outcome-tracker for live/testnet transactions. Falls short because it never touches real node data.
- **Business model sketch:** Free self-hosted crate/daemon (OSS); paid hosted correlation API (per-request or subscription) for teams that don't want to run a Hyperliquid node themselves — similar business shape to Chainstack's dedicated-RPC model for HIP-3 deployers.
- **Scores (1-5):** Evidence 5 / Niche 4 / Big-co neglect 4 / Solo feasibility 4 / Demo-ability 5 / Judging fit 4 / Whitespace 5 → **Total 31/35**

### Z1 — zkreceipt (Zcash Payment Disclosure SDK)
- **Niche user:** Zcash shielded merchants and their buyers settling disputes, exchanges proving customer withdrawals, donors proving matched contributions, OTC desks — reachable via the Zcash Community Forum and Zcash Community Grants (ZCG) applicant pool.
- **Problem (current, 2025-2026):** ZIP 311 ("Zcash Payment Disclosures") defines exactly this need but is still status "Draft," six years after being opened (2020-08-03); Orchard support is an explicit "TODO: Add support for Orchard" in the spec itself, and the spec says "Reference implementation: TBD." As of 2026-09-21 a ZCG grant application (#437, "Zcash Selected-Payment Receipts SDK," $42,000) independently confirms the gap: "developers lack an integrated end-to-end toolkit combining user-controlled export, privacy preview, independent verification, and application binding," even though "existing Zcash primitives support disclosure."
- **Evidence:** (1) VERIFIED — ZIP 311, https://zips.z.cash/zip-0311 — status Draft, TODOs quoted above, four named use cases (event contributions, donation matching, merchant disputes, exchange withdrawals). (2) VERIFIED — ZCG issue #437, https://github.com/ZcashCommunityGrants/zcashcommunitygrants/issues/437 — filed 2026-09-21, "Ready for ZCG Review," milestone 1 not due until 2026-12-22.
- **Why big players won't do it:** Every well-resourced Zcash team (ZODL/Zashi, Zcash Foundation, Electric Coin Co., Shielded Labs) has spent 2026 fully consumed by the zcashd-EOL migration, the emergency Orchard soundness fork (NU6.2, June 2026), and the Ironwood shielded-pool rollout (NU6.3, July 2026) — payment disclosures are a six-year-old "nice to have" ZIP that has never made anyone's critical path.
- **Pure-Rust solution:** A Rust crate built on `librustzcash`/`zcash_client_backend` implementing the ZIP 311 Sapling disclosure format (spend authority via randomized `rk`/`spendAuthSig`, output recovery via the outgoing cipher key `ock`) plus a CLI (`zkreceipt export <txid>` / `zkreceipt verify <disclosure-file>`), scoped to Sapling+transparent at MVP (matching the spec's own current scope) with an Orchard/Ironwood extension path once the ZIP itself defines it. Core technical insight: all the underlying cryptographic primitives already ship in `librustzcash`; the missing piece is the disclosure-object encode/decode/verify layer ZIP 311 specifies but nobody has implemented.
- **14-day solo MVP + demo:** Days 1-3: implement the Sapling disclosure struct + BLAKE2b digest per the spec. Days 4-8: wire spend-authority signature creation/verification and output recovery via `ock` against `zcash_client_backend`. Days 9-11: CLI + a minimal "merchant dispute" reference flow. Days 12-14: polish + demo. **3-minute demo:** a buyer pays a shielded merchant; the merchant claims non-receipt; the buyer runs `zkreceipt export`, hands the file to an independent verifier CLI, which recovers and displays the exact note (amount + memo) without exposing the buyer's full viewing key — resolving the dispute on camera.
- **Track fit:** Zcash ($100k/10).
- **Preliminary competitor scan:** GitHub search "zip311 OR payment-disclosure zcash" → dominated by the core `zcash/zips`, `zcash/zcash`, `zcash/librustzcash` repos themselves (no third-party implementation); the legacy `zcashd` RPC pair `z_getpaymentdisclosure`/`z_validatepaymentdisclosure` was experimental and is being deprecated along with zcashd itself. Closest existing thing: the ZCG grant application #437 describing the same product — but as of research date it is unbuilt (pending committee vote, first milestone due December 2026), leaving a real window to ship first.
- **Business model sketch:** Free OSS crate + CLI; paid integration support/contracts for exchanges and payment processors (BTCPay Zcash plugin, ZGo) who want disclosure built into their checkout/withdrawal flow.
- **Scores (1-5):** Evidence 5 / Niche 4 / Big-co neglect 5 / Solo feasibility 3 / Demo-ability 4 / Judging fit 4 / Whitespace 4 → **Total 29/35**

### E1 — client-migrate (safe Ethereum validator client-migration CLI)
- **Niche user:** Ethereum home/solo stakers who want to switch consensus clients (e.g., off Lighthouse, which holds 38% share) but are afraid of a slashing-causing double-signing window; they gather on r/ethstaker and the EthStaker Discord/survey.
- **Problem (current, 2025-2026):** The EthStaker 2026 staking survey (528 completed responses, 382 from own-capital validators) found client diversity essentially frozen: when asked why they don't migrate off Lighthouse, respondents cited "cost and risk of switching," "reliability," and "slashing risk to migrate" — not preference. The same survey lists "Tax Clarity" and "Privacy & Exposed IP" as the top two practical concerns (32% and 33% respectively), and the community's own tax tool, ethstaker.tax, announced its closure in 2026 because "maintaining the website properly is no longer something I can commit enough time to."
- **Evidence:** (1) VERIFIED — EthStaker Staking Landscape 2026, https://ethstaker.org/staking-landscape-analysis-2026/ — quotes above. (2) VERIFIED — ethstaker.tax closure notice — "After more than five years, the time has come to close ethstaker.tax."
- **Why big players won't do it:** Client diversity is a public good nobody captures value from directly — large staking-as-a-service providers and exchanges have no commercial reason to help a solo staker safely switch open-source clients; the EF funds client teams themselves, not migration tooling between them.
- **Pure-Rust solution:** A Rust CLI that orchestrates a safe cross-client validator migration: exports/validates the EIP-3076 slashing-protection interchange file from the source client, diffs it against the target client's slashing DB to guarantee no gap or overlap in attested epochs, sequences a coordinated shutdown/cooldown/startup (refusing to start the target client until it can prove the source is fully stopped and the interchange import succeeded), and produces a signed audit log of the whole migration. Core technical insight: the EIP-3076 interchange format is already standardized across clients; nobody ships the orchestration/verification layer around it as a single trustworthy tool.
- **14-day solo MVP + demo:** Days 1-4: parse and validate EIP-3076 JSON from Lighthouse and one target client (e.g., Teku or Nimbus). Days 5-9: build the gap/overlap checker + shutdown-sequencing state machine against local testnet clients. Days 10-12: CLI UX + signed audit log. Days 13-14: polish + demo on a local devnet. **3-minute demo:** run `client-migrate lighthouse->teku` on a devnet validator; watch it verify the source is stopped, diff the slashing DB with zero gap, import, and bring up the target client — with a "double-sign risk: none detected" report on screen.
- **Track fit:** Ethereum L1 ($25k/5).
- **Preliminary competitor scan:** GitHub search "validator client migration slashing protection" → 0 dedicated repos found. Closest existing thing found: `nklave` (crates.io, Feb 2026), a Web3Signer-compatible **remote signer** with its own EIP-3076 interchange/storage layer — adjacent (same standard) but solves a different problem (centralized remote signing, not client-to-client migration safety) and doesn't reduce this idea's whitespace much.
- **Business model sketch:** Free OSS tool; the natural monetization is thin (staking-pool operators might pay for a fleet-migration version), which is the idea's weakest point — it's closer to a public good than a business.
- **Scores (1-5):** Evidence 4 / Niche 4 / Big-co neglect 4 / Solo feasibility 3 / Demo-ability 3 / Judging fit 4 / Whitespace 4 → **Total 26/35**

### R1 — scaled-balance (corrected-balance crate for tokenized stocks)
- **Niche user:** Third-party indexers, wallets, portfolio trackers, and lending-protocol risk engines integrating Robinhood Chain stock tokens (ERC-8056 `uiMultiplier`) and/or Solana xStocks (Token-2022 Scaled UI Amount extension).
- **Problem (current, 2025-2026):** Corporate actions (dividends, splits, reverse splits) on both platforms are implemented as a multiplier update, not a balance rebase — "raw balances and Transfer values stay fixed" while `uiMultiplier()` changes. Most integrations don't apply it: on Robinhood Chain, RWA.xyz found that "across the 21 mismatched tokens we identified, reported supply was overstated by roughly 64,000 tokens, a 56% discrepancy" (2026-01-23); on Solana xStocks, a hackathon post-mortem states plainly "every application is expected to fetch [the multiplier] and apply it themselves. Most dont," which is why "Kamino Finance already runs a price-band mechanism around corporate-action windows on its xStocks lending markets" as a defensive workaround.
- **Evidence:** (1) VERIFIED — RWA.xyz, https://app.rwa.xyz/blog/robinhoods-tokenized-stocks-the-good-the-bad-and-the-fix. (2) VERIFIED — Robinhood Chain developer docs, https://docs.robinhood.com/chain/building-with-stock-tokens/ — "The multiplier scales the effective amount without changing raw balances or total supply." (3) VERIFIED — GODGRACE07/multiplier README (GitHub) — quotes above.
- **Why big players won't do it:** Robinhood and Chainlink already solve this correctly for anyone reading their own docs (the Chainlink price feed bakes the multiplier in); the neglect is a long tail of third-party integrators who didn't read carefully — not a gap any single vendor is incentivized to patch for everyone else's code.
- **Pure-Rust solution:** A Rust crate + small daemon that watches both `TransferWithScaledUI`/`UIMultiplierUpdated` events (EVM/Robinhood Chain) and Token-2022 Scaled UI Amount multiplier updates (Solana), normalizes them into one corrected-balance model, and exposes it as an embeddable library (for Rust-based indexers/risk engines) and a query API — differentiated from every competitor found by being a dependency other software links against, not another dashboard.
- **14-day solo MVP + demo:** Days 1-4: decode ERC-8056 events on Robinhood Chain via a testnet/mainnet RPC. Days 5-8: decode Token-2022 Scaled UI Amount updates on Solana. Days 9-12: unify into one crate API + demo indexer. Days 13-14: polish. **3-minute demo:** side-by-side "naive vs. corrected" balance for a token that just paid a dividend, on both chains, updating live.
- **Track fit:** Robinhood Chain ($25k/5) and/or Solana ($100k/10) — a genuine dual-track integration if judged as such.
- **Preliminary competitor scan:** GitHub search found real, recent, but non-Rust competitors: `AlperJ/exdate` ("The brokerage statement that tokenized stocks never send you," TypeScript, pushed 2026-09-13), `GODGRACE07/multiplier` (TypeScript, 2026-09-17), `kinexbtdev/rh-indexer` (TypeScript, 2026-08-31). crates.io search for "scaled-ui-amount" and "corporate-action" → 0 results. Falls short of a Rust-native answer, but the *feature* whitespace is thinner than H1/Z1 — this is closer to "same idea, wrong language" than "nobody has built this."
- **Business model sketch:** Free crate; paid hosted correction API for lending protocols that want a real-time solvency-safe price feed.

### D1 — noncewarden (self-hosted durable-nonce lifecycle daemon)
- **Niche user:** Solana DAO/protocol treasuries and Squads multisig admins who create durable-nonce accounts for offline/hardware-wallet signing workflows.
- **Problem (current, 2025-2026):** Durable nonces "remain valid indefinitely until the nonce is advanced," and per Chainalysis, "the signer has no way to revoke their approval once it is given, unless the nonce account is manually advanced, which most users do not monitor." This exact gap enabled the $285.3M Drift Protocol hack (2026-04-01): the attacker had two signers pre-sign transactions on 2026-03-23 and executed them a week later.
- **Evidence:** (1) VERIFIED — Chainalysis, https://www.chainalysis.com/blog/lessons-from-the-drift-hack/. (2) VERIFIED — BlockSec post-mortem, https://blocksec.com/blog/drift-protocol-incident-multisig-governance-compromise-via-durable-nonce-exploitation.
- **Why big players won't do it:** Existing responses focus on detection/scanning at sign-time (a SaaS business model for security firms), not on removing the root cause (nonces that never expire by default) — proactive lifecycle management is less "sellable" as a security product than a scary pre-sign warning.
- **Pure-Rust solution:** A self-hosted Rust daemon that watches an org's own durable-nonce accounts and enforces a policy (e.g., "auto-advance if unused for N hours," alert on any nonce-account creation not on an allow-list) using a separate, narrowly-scoped advance-authority key — shrinking the attack window from "indefinite" to "policy-defined," rather than just alerting a human who may not act in time.
- **14-day solo MVP + demo:** Days 1-5: nonce-account watcher + policy engine. Days 6-10: auto-advance execution with a scoped key. Days 11-13: alerting + dashboard. Day 14: demo. **3-minute demo:** create a nonce account, "forget" about it, watch `noncewarden` auto-advance it after the policy window expires, closing the Drift-style attack window live.
- **Track fit:** Solana ($100k/10); cross-chain security angle named in the brief.
- **Preliminary competitor scan:** This space is **crowded and moved fast post-Drift**: `Sec3` ships a free "Nonce & Multisig Monitoring" tool, `txscope-hq/txscope` (GitHub, 2026-04-05) is a pre-sign threat scanner, `AaronTan11/solana-nonce-guard` (GitHub, 2026-04-02) detects nonce attack vectors, and Custos Nox offers real-time attack monitoring — all of these are *detection* tools a human must act on, none found do *automatic, policy-based, self-hosted expiry*, but a judge will see a crowded field at a glance and discount novelty accordingly.
- **Business model sketch:** Self-hosted OSS; paid managed version for DAOs that don't want to run infrastructure.
- **Scores (1-5):** Evidence 4 / Niche 3 / Big-co neglect 2 / Solo feasibility 4 / Demo-ability 3 / Judging fit 3 / Whitespace 2 → **Total 21/35**

### Rejected ideas (one line each)
- **Squads/Solana pre-sign verification CLI** — `msig` (Solana-Multisig-Tools/multisig-cli) already decodes, simulates, shows the Ledger message hash, and supports air-gapped `.sqds` signing.
- **General durable-nonce attack detection** — Sec3's free tool, `txscope-hq/txscope`, and `AaronTan11/solana-nonce-guard` all shipped within weeks of the Drift hack (April 2026).
- **Zcash FROST shielded-multisig kit** — Zkool already ships FROST multisig in a mobile/desktop wallet; the Zcash Foundation's own `frost-core`/`frostd`/`frost-client` stack is production-ready; Zigner adds an air-gapped hardware option.
- **zcashd→Zebra/Zallet compatibility shim** — Zakura (Valar Group + Project Tachyon) is a fully independent, actively-updated Rust node (v1.5.0, pushed 2026-09-24) that reproduces the legacy zcashd RPC interface specifically for this migration.
- **Hyperliquid historical L2 book/fill data product** — Hydromancer's Reservoir, 0xArchive, and CryptoHFTData already sell maintained, gap-filled data on top of Hyperliquid's own best-effort S3 archive.
- **HIP-3 oracle-updater infrastructure** — a tiny (sub-dozen), well-capitalized deployer population already courted by RPC vendors (Chainstack, SEDA); not a "big co won't serve this" gap.
- **Small-Solana-validator cost tooling** — the underlying pain is protocol-level vote-fee economics, which Alpenglow (targeted Q4 2026) fixes directly; no amount of third-party software changes the unit economics.
