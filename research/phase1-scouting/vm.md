### VM-01 — Solana Runtime-Change Impact Simulator ("simd-diff" / "redeploy-radar")
- **Niche user (who exactly; roughly how many; where they gather):** Solana program upgrade authorities / maintainers of already-deployed, long-tail programs that must redeploy before SIMD-0500 locks out old bytecode versions — specifically the operators of the **17,279 upgradeable programs still on SBPFv0** (per SIMD-0500's own stats) plus anyone whose program uses patterns that SIMD-0459/0460 change (stack address dependence, CPI account-realloc edge cases). Gather on Solana Stack Exchange, #dev-support on Solana Tech Discord, Anza/Firedancer GitHub, r/solana dev threads.
- **Problem (concrete, current 2025-2026):** Two converging deadlines: (1) SIMD-0500 (status "Review" as of research; Anza's blog targets Agave v4.4 / ~Nov 2026) will reject any new deployment/upgrade/finalize of SBPFv0/v1/v2 bytecode — forcing a mandatory rebuild+redeploy of thousands of live programs; a broken rebuild silently produces `call -1` bytecode that deploys fine but hits `CallDepthExceeded` at runtime. (2) SIMD-0459/0460 (already active on testnet/devnet, pending mainnet) tighten CPI/stack/memory semantics; Anza's own SIMD-0460 doc admits this "can affect programs which rely on the address space layout of the stack ... or being dependent on bugs." Today, developers have no way to take *their specific deployed program* and ask "will replaying real recent mainnet traffic against my rebuilt/upgraded binary produce the same state, logs, and CU cost?" — they either eyeball a diff or redeploy and pray.
- **Evidence (>=2 primary-source links; quote the key line; mark VERIFIED/UNVERIFIED):**
  1. SIMD-0500 proposal — VERIFIED (fetched): "Loader-v3 (Upgradable): 17,279 programs using SBPFv0; 12 using v1; 41 using v2." https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0500-disable-deployment-of-sbpf-v0-v1-v2.md
  2. Anza migration blog — VERIFIED (fetched): "reject deployments, upgrades, and finalizations of any program built for a bytecode version older than SBPFv3" and the `call -1` / `CallDepthExceeded` footgun from undeclared `extern "C"` syscalls. https://www.anza.xyz/blog/migrating-solana-programs-to-sbpfv3
  3. SIMD-0460 — VERIFIED (fetched): "Removing the stack frame gaps globally (even for SBPFv0) programs can affect programs which rely on the address space layout of the stack." https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0460-virtual-address-space-adjustments.md
  4. anchor-litesvm issue #3 (Sept 22, 2026) — VERIFIED (fetched): real-world breakage from ELF-format mismatch between platform-tools v1.57's v3 output and litesvm/agave's parser: "solana-sbpf 0.13.1's strict parser requires e_machine == EM_SBPF (263) ... but v1.57's sbpfv3 target emits e_machine as 247." https://github.com/brimigs/anchor-litesvm/issues/3
  5. Surfpool PR #786 (open, Aug 27–Sept 14 2026) — VERIFIED (fetched): `surfpool profile <TX_SIGNATURE>` re-executes a mainnet tx locally, but a reviewer flagged: "transaction therefore executes under runtime rules that were not active at its original slot, causing misleading errors" — i.e. the closest existing tool has an open correctness bug and no program-override capability. https://github.com/solana-foundation/surfpool/pull/786
- **Why big players won't do it:** Anza/Firedancer own the protocol change, not per-project migration risk; Solana Foundation's own `feature-activation-verifier` is generic infra (tests whole feature gates in the abstract, not "is *my* deployed program at risk") and is pre-1.0 (1 star, only 3 of 20+ relevant SIMDs covered as of research). No foundation team is going to build a bespoke "will my specific program survive this SIMD" tool for a long tail of small/abandoned projects — that's exactly the niche/reachable-but-unprofitable gap.
- **Pure-Rust solution (what ships):** A Rust CLI + library (`simd-diff`) built on LiteSVM/solana-svm: (1) fetch N recent real transactions that touched a target program via RPC `getSignaturesForAddress`; (2) replay each under the *current* runtime config against the *existing* deployed binary (baseline) and again with the binary swapped for a candidate rebuild (sBPFv3, or with a specific feature gate flipped); (3) diff return data, logs, CU consumption, and resulting account state; (4) run a static pass over the candidate ELF flagging known footguns (unresolved syscalls -> `call -1`, absolute stack-address patterns) before even trying to replay. Ships as `cargo install simd-diff`, JSON + human-readable diff report, exit code for CI.
- **14-day solo MVP + what a 3-minute demo shows:** Days 1-4: LiteSVM harness that loads a real program-data account + N recent txs from a pinned devnet/mainnet snapshot and replays them; days 5-8: binary-swap + diff engine (logs/CU/state); days 9-11: static footgun linter for the `extern "C"` / `call -1` case and stack-address heuristic; days 12-14: CLI polish + demo script. Demo: pick a real, currently-SBPFv0, still-upgradeable mainnet program; rebuild it for sBPFv3 (one with a deliberately reintroduced bug); run `simd-diff` and show it catching the CU regression / `CallDepthExceeded` before deployment, side-by-side with "this old binary" vs "this new binary" transaction diffs.
- **Track fit:** Solana ($100k/10) — direct hit, this is pure Solana core-infra tooling tied to a named, dated protocol change.
- **Preliminary competitor scan:** Searched GitHub (`sbpfv3`, `sbpf v3`, `simd-0500`), crates.io, Colosseum gallery (JS-rendered, could not enumerate — see note in Rules section below). Closest existing things: **UpgradeGuard** (VictorGSoutoXP, pre-MVP hackathon repo, Sept-Oct 2026, 0 stars/10 commits) — does static repo analysis only ("Cargo versions, toolchain pins, build flags, syscall imports"); README explicitly lists bytecode analysis/transaction replay/binary diffing as "planned," not built. **SolanaRepro** (caiomodesti, 0 stars/5 commits) — does replay+diff but MVP scope is narrow: "Supported transaction classes (MVP): SOL transfers, classic SPL token transfers, deterministic system failures. Unsupported: complex CPI, ALT reconstruction, Token-2022, DeFi protocols" — exactly the complex-CPI programs most at risk from SIMD-0459/0460 are the ones it can't handle. **Surfpool `profile`** — single-tx, no binary override, open correctness bug (see evidence #5), unmerged as of Sept 14 2026. **feature-activation-verifier** (Solana Foundation) — generic feature-gate pass/fail matrix, only 3/20+ SIMDs implemented, not per-program. None of these combine (a) real recent-tx replay, (b) binary-swap diffing, and (c) the specific sBPFv3 static footgun checks in one tool.
- **Business model sketch:** Free OSS CLI for individual devs (adoption/trust); paid hosted CI service ($/month) for protocols/DAOs that want automatic "pre-upgrade replay report" gating on every program upgrade PR, priced like a security-tooling SaaS (Tenderly/OpenZeppelin Defender-style). Audit firms (OtterSec, Zellic, Sec3) are a plausible channel/reseller since this replaces a manual workflow they currently do by hand.
- **Scores 1-5:** Evidence 5 / Niche 4 / Big-co neglect 4 / Solo feasibility 4 / Demo-ability 5 / Judging fit 4 / Whitespace 4 -> **total 30/35**

### VM-02 — HyperEVM CoreWriter Outcome Tracer ("corewriter-verify")
- **Niche user (who exactly; roughly how many; where they gather):** Rust/Solidity developers building HyperEVM contracts that write to HyperCore via `CoreWriter` (perp vaults, LSTs, market-making bots, HIP-3 deployers) — a small, nameable, growing set of teams building in the Hyperliquid builders track (visible via hyperliquid-dev GitHub org, Hyperliquid Discord #hyperevm-dev, the ecosystem list of ~10-20 active CoreWriter-integrated projects found in this research: hyper-evm-lib consumers, hypervault, native-markets, etc.).
- **Problem (concrete, current 2025-2026):** `CoreWriter.sendRawAction()` is fire-and-forget: the EVM transaction succeeds and emits a `RawAction` log whether or not HyperCore actually accepts the action. If the action is malformed, the account isn't initialized on Core yet, or a limit order gets rejected (tick size, min notional, margin, etc.), **HyperCore drops it silently — no revert, no error event.** Two fresh, unanswered GitHub issues (Sept 21, 2026) from the same reporter show real developers hitting this in production-adjacent testing: spot orders and transfers show "status 1, correctly-decoded RawAction event" on EVM but "zero HyperCore-side effect," with no diagnostic path.
- **Evidence:**
  1. hyperliquid-dex/node issue #172 (Sept 21, 2026) — VERIFIED (fetched): "All succeeded on EVM (status 1, correctly-decoded RawAction event) and all produced zero HyperCore-side effect." Reporter tried encoding validation, notional/lot checks, slippage, fresh wallet — no root cause found, issue open/unanswered. https://github.com/hyperliquid-dex/node/issues/172
  2. hyperliquid-dex/node issue #171 (Sept 21, 2026) — VERIFIED (fetched): "never fill on HyperCore — no fill, no open order, no error" for programmatic buy orders specifically (sells + UI buys work). https://github.com/hyperliquid-dex/node/issues/171
  3. Chainstack docs (CoreWriter guide) — VERIFIED (fetched): "sendRawAction emits its log and the EVM transaction succeeds whether or not HyperCore accepts the action... HyperCore drops it silently—no EVM revert, no error event, and the order simply never appears in openOrders." https://docs.chainstack.com/docs/hyperliquid-corewriter
  4. hyper-evm-lib README — VERIFIED (fetched): confirms the same precompile-staleness gotcha and recommends manual state-polling, not automated correlation. https://github.com/hyperliquid-dev/hyper-evm-lib
- **Why big players won't do it:** This is a narrow cross-layer debugging problem specific to Hyperliquid's unique dual-VM architecture; Hyperliquid Labs' own docs push the burden onto developers ("query `/info` ... or read precompiles ... or monitor the L1 explorer") rather than shipping a correlation tool. It's too Hyperliquid-specific for general EVM tooling vendors (Tenderly, Foundry) to prioritize, and too devtool-y (not a dApp) for Hyperliquid's own small core team to build ahead of bigger roadmap items.
- **Pure-Rust solution (what ships):** A Rust daemon/CLI (`corewriter-verify`) that: (1) watches HyperEVM `RawAction` logs (decoding all documented action IDs: limit order, vault transfer, USD class transfer, token delegate, etc.) in real time via HyperEVM RPC/websocket; (2) for each action, polls the HyperCore `/info` endpoint (`orderStatus`, `clearinghouseState`) and correlates by user+nonce+timing window; (3) surfaces a structured outcome — success, or one of the ~28 documented HyperCore rejection reasons (`tickRejected`, `minTradeNtlRejected`, `insufficientSpotBalanceRejected`, etc.) — back to the developer as a webhook/CLI stream/local dashboard; (4) flags the specific known footgun (account not yet initialized on Core in the same block) before submission via a pre-flight check.
- **14-day solo MVP + what a 3-minute demo shows:** Days 1-3: RawAction decoder for the documented action ID set; days 4-7: HyperCore `/info` polling + correlation logic (by user address + nonce/sequence + time window) on testnet; days 8-10: rejection-reason mapping + pre-flight account-existence check; days 11-14: CLI/dashboard + demo. Demo: submit a CoreWriter limit order on HyperEVM testnet that's deliberately malformed (bad tick) alongside one that's valid; show the tool live-labeling one "EVM: success / Core: tickRejected" and the other "EVM: success / Core: filled" — the exact scenario from issue #172 diagnosed in seconds instead of never.
- **Track fit:** Hyperliquid ($100k/10, HyperCore or HyperEVM) — direct hit, squarely in the dual-VM execution seam the track calls out.
- **Preliminary competitor scan:** Searched GitHub (`corewriter`, `hyperevm hypercore`), crates.io. 9 CoreWriter-related repos found, all narrower: **hyper-evm-lib** (Solidity, local Foundry-only simulation, no live outcome correlation) — https://github.com/hyperliquid-dev/hyper-evm-lib. **corewriter-trace** (cosullivan, TS/Next.js, decodes RawAction logs only, no outcome correlation, proprietary license) — https://github.com/cosullivan/corewriter-trace. **hyperevm-hypercore-indexer** (envio, TS, indexes RawAction + transfer logs into GraphQL; README explicitly states it does *not* handle the reverse Core->EVM direction and does not correlate outcomes) — https://github.com/enviodev/hyperevm-hypercore-indexer. The `hl-node --write-system-and-core-writer-actions` flag exists at the infra layer but requires running a full Hyperliquid node and its output schema is undocumented in the public gitbook (confirmed: the L1-data-schemas page has no entry for this file). No tool automatically correlates action -> outcome without running your own node or manually polling.
- **Business model sketch:** Free CLI/self-host for solo devs; hosted webhook/alerting SaaS for teams running CoreWriter-dependent protocols in production (LST issuers, vault protocols) who need real-time alerting when actions silently fail — priced per-project like a monitoring tool (Sentry/Tenderly Alerts style).
- **Scores 1-5:** Evidence 5 / Niche 4 / Big-co neglect 4 / Solo feasibility 4 / Demo-ability 5 / Judging fit 4 / Whitespace 4 -> **total 30/35**

### VM-03 — zkVM Accelerator Conformance & Differential Test Kit ("accel-conform")
- **Niche user (who exactly; roughly how many; where they gather):** Core engineers on RISC-V zkVM teams implementing the eth-act `zkvm_accelerators.h` standardized C interface (SP1/Succinct, RISC Zero, OpenVM, ZisK, Airbender, Jolt, Pico — roughly 6-8 named teams) plus guest-program authors who rely on "patched crates" for correctness-critical crypto (ecrecover, BLS12-381 pairing for consensus/rollup proving). Gather on the eth-act GitHub org, Ethereum R&D Discord (#zkevm-standards channel referenced in the standards repo), and each zkVM's own Discord/Telegram.
- **Problem (concrete, current 2025-2026):** The Ethereum Foundation's `eth-act/zkevm-standards` project defines a shared C ABI (`zkvm_accelerators.h`) so guest programs can call one portable interface for ecrecover, SHA-256, RIPEMD-160, modexp, BN254/BLS12-381 ops, blake2f, KZG, etc. across any conformant zkVM — but **there is no shared conformance/test-vector suite**, and two independent, soundness-relevant bugs were found by hand in 2026: OpenVM's `zkvm_secp256k1_ecrecover` returned a wrong public key while reporting success (`ZKVM_EOK`), and SP1's BLS12-381 accelerator had incorrect Fp2 encoding and infinity-point handling vs. EIP-2537. Both were found by one-off manual comparison against a native reference, not by any standing test harness — the open GitHub issue asking the EF to "provide reference implementation of IO and accelerators libraries... that could be used for cross-checking with vendor implementations" has been open since March 2026 with zero engagement.
- **Evidence:**
  1. eth-act/zkevm-standards `zkvm_accelerators.h` — VERIFIED (fetched): the actual header defining ~17 EVM-precompile-equivalent accelerator functions, each returning `ZKVM_EOK`/`ZKVM_EFAIL`. https://github.com/eth-act/zkevm-standards/blob/main/standards/c-interface-accelerators/zkvm_accelerators.h
  2. openvm-org/openvm issue #3147 (Sept 3, 2026) — VERIFIED (fetched): "Accelerated zkvm_secp256k1_ecrecover returns a wrong public key with ZKVM_EOK (v2.1.0-preview)" — found via known-answer differential testing by an outside reporter, not internal CI. https://github.com/openvm-org/openvm/issues/3147
  3. succinctlabs/sp1 issue #2881 (July 13, 2026) — VERIFIED (fetched): "Incorrect infinity point and Fp2 encoding/decoding in zkvm_accelerators.h's BLS12-381 curve operations," found by comparing against EIP-2537 spec by hand; reporter also opened a companion clarification issue on zkevm-standards (#35). https://github.com/succinctlabs/sp1/issues/2881
  4. eth-act/zkevm-standards issue #16 (open since March 11, 2026) — VERIFIED (fetched): "EF to provide reference implementation of IO and accelerators libraries... That could be used for cross-checking with vendor implementations of the corresponding libraries." No comments, no PR, not built. https://github.com/eth-act/zkevm-standards/issues/16
  5. zkvmBlast README (zksecurity, pushed Aug 10, 2026) — VERIFIED (fetched): confirms scope is RISC-V *instruction execution* differential fuzzing (SP1/RISC0/OpenVM/Pico/Zisk/Airbender vs. Spike reference), with a `--with-precompiles` flag that only patches crates for perf comparison — grepped the full README for "accelerat|zkvm_" and found **no mention of the standardized C accelerator interface or known-answer correctness testing of it**. https://github.com/zksecurity/zkvmblast
- **Why big players won't do it:** Each zkVM team builds and tests its own accelerator in isolation (that's how both bugs shipped past internal review); the EF's own zkevm-standards repo is a *specification* body, not a test-infra builder — issue #16 asking them to build exactly this has sat unaddressed for 6+ months. zkvmBlast (zksecurity, the closest well-funded differential-fuzzing effort) deliberately scoped itself to ISA-level execution, not the accelerator layer — a reasonable, disclosed choice that leaves this specific gap open.
- **Pure-Rust solution (what ships):** A Rust crate + CLI (`accel-conform`) providing: (1) a corpus of known-answer test vectors for every function in `zkvm_accelerators.h` sourced from existing spec test vectors (EIP-2537 for BLS12-381, EIP-198 for modexp, standard secp256k1/BN254 vectors, RFC test vectors for hashes); (2) a small guest-program harness (using `ere`, the eth-act unified zkVM interface, to avoid reinventing per-zkVM plumbing) that runs each vector through the real accelerator on each target zkVM and checks status code + output against the known answer, flagging exactly the OpenVM/SP1-style "EOK but wrong" class of bug; (3) a differential mode that cross-checks all zkVMs against each other and against a pure-Rust reference implementation for the same primitive.
- **14-day solo MVP + what a 3-minute demo shows:** Days 1-4: known-answer vector corpus (reuse existing EIP/RFC test vectors, no need to invent), plus guest harness scaffolding via `ere`; days 5-9: wire up 2-3 zkVMs (SP1 + OpenVM minimum, since both have confirmed bugs to reproduce) and the ecrecover/BLS12-381 checks specifically; days 10-12: differential cross-zkVM report format; days 13-14: polish + demo. Demo: run `accel-conform` against SP1 and OpenVM live, showing it catching the exact two real bugs found in this research (BLS12-381 infinity/Fp2 encoding on SP1, secp256k1_ecrecover wrong-key-with-EOK on OpenVM) in seconds — a concrete "this tool would have caught a live, disclosed soundness bug" demo.
- **Track fit:** Ethereum L1 ($25k/5) primarily (zkEVM/stateless-validation infra is core L1 roadmap territory); secondary relevance to any track whose rollup/zkVM story depends on correct EVM-precompile semantics.
- **Preliminary competitor scan:** Searched GitHub (`arguzz`, `zkvmblast`, `zkevm-standards`), eth-act org repo listing (35+ repos enumerated via API). Closest things: **zkvmBlast** (zksecurity) — ISA-level differential fuzzing, confirmed no accelerator-interface coverage (see evidence #5). **Arguzz** (academic, USENIX Security 2026) — metamorphic testing for zkVM *proving soundness* of arbitrary guest code, not targeted at the standardized accelerator ABI; found soundness bugs but at the constraint-system level (e.g., Jolt's `lui` instruction), a different layer from "does the accelerator compute the right answer." **zkevm-test-monitor** (eth-act, ACT4 framework) — RISC-V *ISA compliance* testing, explicitly not accelerator/precompile correctness. No existing tool combines known-answer + cross-zkVM differential testing specifically for `zkvm_accelerators.h`.
- **Business model sketch:** Open-source test suite as a public good (Public Goods Award $5k fits directly); revenue via paid "conformance certification" / CI-badge service for zkVM teams and rollups that want to advertise accelerator correctness, plus consulting engagements with zkVM teams to integrate the suite into their CI (similar to how ACT4/RISC-V compliance testing became a paid-adjacent service).
- **Scores 1-5:** Evidence 5 / Niche 3 / Big-co neglect 4 / Solo feasibility 3 / Demo-ability 4 / Judging fit 4 / Whitespace 5 -> **total 28/35**

### VM-04 — Stylus Program Lifecycle Guardian ("stylus-keepalive")
- **Niche user (who exactly; roughly how many; where they gather):** Teams deploying Rust/WASM smart contracts via Arbitrum Stylus — on Arbitrum One/Nova today, and prospectively on Robinhood Chain (confirmed built on Arbitrum Orbit/Nitro, so Stylus is available there too). Named teams from Arbitrum's own ecosystem posts: OpenZeppelin, thirdweb, RedStone, Fiet Protocol, 9Lives, DeBid, Jetstream, Lit Protocol — a small, growing, nameable set gathering on the Arbitrum Stylus Discord/forum and the `OffchainLabs/stylus-sdk-rs` GitHub.
- **Problem (concrete, current 2025-2026):** Stylus contracts are not "deploy and forget." Per Arbitrum's own docs: every activated program **expires after 365 days** (configurable `ExpiryDays`) and reverts to uncallable until `codehashKeepalive`/re-activation; separately, **ArbOS protocol upgrades can invalidate activation outright** — the `ArbOS 60/61 "Elara"` upgrade (Aug 2026) states "Contracts relying on multi-value WASM will no longer be able to be activated or reactivated," meaning some already-deployed contracts became *permanently* unreactivatable on that upgrade, not just due-for-renewal. There is no dedicated monitoring tool that watches a fleet of deployed Stylus contracts and warns before either failure mode.
- **Evidence:**
  1. Arbitrum docs, "Activation" — VERIFIED (fetched): "Programs expire after the chain's configurable ExpiryDays parameter, which defaults to 365 days from activation... `ProgramNeedsUpgrade` error if... Program version incompatible with current Stylus version," plus the `programTimeLeft()` / `codehashKeepalive()` ArbWasm precompile methods that exist precisely because this is a known operational burden. https://docs.arbitrum.io/stylus/concepts/activation
  2. Arbitrum Foundation blog, "ArbOS Elara" (Aug 20, 2026) — VERIFIED (fetched): "Contracts relying on multi-value WASM will no longer be able to be activated or reactivated" following the upgrade — a hard, dated breaking change, not a hypothetical. https://blog.arbitrum.io/arbos-elara/
  3. Robinhood Chain built on Arbitrum Orbit/Nitro — VERIFIED (fetched, WebSearch synthesis of Arbitrum's own testnet launch post): confirms the same Stylus lifecycle mechanics apply to the newest track chain in this hackathon, not just legacy Arbitrum. https://blog.arbitrum.io/robinhood-chain-testnet/
- **Why big players won't do it:** Arbitrum/OffchainLabs ship the protocol-level precompile (`ArbWasm.programTimeLeft`) and expect individual teams to build their own ops tooling around it — this is standard "we give you the primitive, you build the runbook" behavior from a foundation with dozens of higher-priority roadmap items (ArbOS releases, Stylus SDK features per the open GitHub issue backlog). No general-purpose EVM monitoring vendor (Tenderly, OpenZeppelin Defender) has Stylus-specific expiry/version-compatibility logic since Stylus is Arbitrum-only and niche relative to their EVM-wide customer base.
- **Pure-Rust solution (what ships):** A Rust CLI/daemon (`stylus-keepalive`) that: (1) takes a list of deployed Stylus contract addresses; (2) polls `ArbWasm.programTimeLeft()` and `codehashVersion()` on a schedule; (3) alerts (webhook/Slack/CLI) when a contract crosses a configurable days-remaining threshold, and separately detects version-incompatibility risk ahead of an announced ArbOS upgrade by checking the contract's WASM features (e.g., multi-value usage) against the upcoming ArbOS's compatibility notes; (4) optionally auto-submits the `codehashKeepalive` transaction once the 31-day minimum age is met.
- **14-day solo MVP + what a 3-minute demo shows:** Days 1-4: ArbWasm precompile client (`programTimeLeft`, `codehashVersion`, `codehashKeepalive`) in Rust over an Arbitrum RPC; days 5-8: polling daemon + alert thresholds + simple dashboard; days 9-11: static WASM-feature check (multi-value detection) against a target contract's stored bytecode, flagged against known ArbOS compatibility breaks; days 12-14: polish + demo. Demo: point the tool at a handful of real testnet Stylus deployments (including one deliberately close to expiry), show live countdown + alert firing, then show the multi-value-WASM compatibility check flagging a contract that would break on the next Elara-style upgrade before it happens.
- **Track fit:** Arbitrum ($25k/5) primary; Robinhood Chain ($25k/5) secondary given shared Orbit/Stylus stack — a single MVP plausibly qualifies for both tracks.
- **Preliminary competitor scan:** Searched GitHub API (`stylus+expir`, `stylus+keepalive`, `arbwasm+monitor`, `programTimeLeft`) — **zero repositories returned for any of the four queries.** Also checked `cargo-stylus` (OffchainLabs' own CLI): it has `check`/`activate`/`cache` subcommands but these are manual, one-shot operations, not a monitoring daemon; its open-issue backlog (9 open issues on `cargo-stylus`, 15 on `stylus-sdk-rs`, checked via API) contains no expiry-monitoring feature requests. Confirmed: no dedicated expiry/compatibility-watchdog tool exists.
- **Business model sketch:** Free tier for a handful of contracts (solo devs); paid fleet-monitoring SaaS for protocols with many Stylus deployments (OpenZeppelin-style customers), priced per-contract/month like uptime/monitoring tooling (Tenderly Alerts, Defender Sentinels).

### VM-05 — Solana Program Upgrade Diff-for-Humans ("upgrade-lens")
- **Niche user (who exactly; roughly how many; where they gather):** Multisig signers and DAO/protocol governance participants who must approve a Solana program upgrade without being the engineer who wrote the diff — Squads multisig members, security councils, and community reviewers voting on upgrade transactions. A concretely nameable group: every team using Squads v4 for program-upgrade authority (Squads itself calls out this exact review step in its own security docs), gathering on the Squads Discord, Solana Security Alliance (SEAL) framework docs, and DAO governance forums.
- **Problem (concrete, current 2025-2026):** When a multisig signer is asked to approve a program upgrade, they see a buffer account and a program ID — not "what actually changed in the code." SEAL's own published wallet-security framework, written specifically to harden Squads signing workflows, admits: **"Limited tooling is available for Solana verification compared to EVM. Exercise extra caution and cross-verify with team members."** Today's best practice is: rebuild from source yourself, run `solana-verify`, and manually diff two `.so` files or two source trees by eye — there is no tool that decompiles/summarizes *what instructions, account checks, or CPI targets changed* between the currently-deployed binary and the pending buffer, in a form a non-engineer signer can sanity-check in the 60 seconds before clicking approve. This is the exact "program upgrade diffing" gap named in this research's own seed list, and it is now more urgent because SIMD-0500 (see VM-01) is forcing a wave of mandatory rebuild-and-upgrade transactions across the ecosystem in the next few months, each one needing this same signer review.
- **Evidence:**
  1. SEAL Solana Wallet Security framework — VERIFIED (fetched): "Limited tooling is available for Solana verification compared to EVM. Exercise extra caution and cross-verify with team members." No buffer-diff or upgrade-content-summary tool named anywhere on the page (checked: covers SOL transfers, token transfers, and config-change verification only, not program-code changes). https://frameworks.securityalliance.org/wallet-security/signing-and-verification/secure-multisig-squads-verification/
  2. `solana-verify` / Squads docs — VERIFIED (fetched, via WebSearch synthesis): confirms the current recommended workflow is "verify that the on-chain buffer matches the program source code using Ellipsis Labs's verifiable build" — i.e. verifies *authenticity* (does the buffer match a given source repo) but not *content* (what changed vs. the currently-live version) — a different, narrower guarantee than a diff.
  3. GitHub search for existing tools (this session, via API) — VERIFIED: two very early sBPF decompiler projects exist (`SpriteDay/sbpf-decompiler`, created Sept 12 2026, 0 stars; `owizdom/SBPF-3-1`, created Jan 6 2026, 0 stars) confirming raw decompilation capability is nascent and unpackaged — neither is positioned as an upgrade-review/diff tool, both are generic "decompile this .so" utilities.
- **Why big players won't do it:** This sits at the intersection of two niches nobody big owns end-to-end: Squads builds the signing UX (not bytecode analysis), Anza/Firedancer build the runtime (not human-readable diffing), and security firms (OtterSec, Zellic, Sec3) do this by hand as billable audit work rather than shipping a free/cheap self-serve tool that would cannibalize that billable work. SEAL's own docs explicitly flag the tooling gap rather than filling it.
- **Pure-Rust solution (what ships):** A Rust CLI/library (`upgrade-lens`) that takes two sBPF ELF binaries (currently-deployed vs. pending buffer) and produces a structured, human-readable diff: changed/added/removed instruction handlers (by discriminator where Anchor IDL is available, falling back to CFG-level function boundaries otherwise), changed CPI call targets (which external program IDs are invoked, a critical signer-relevant fact), changed account-ownership/signer checks (pattern-matched from the sBPF control-flow graph), and a plain-English summary line per change. Built on `solana_rbpf`/`sbpf` disassembly libraries plus a lightweight CFG-diff pass — genuinely a "decompile enough to diff meaningfully," not a full decompiler.
- **14-day solo MVP + what a 3-minute demo shows:** Days 1-4: ELF loading + sBPF disassembly + basic CFG extraction (reuse `solana_rbpf`); days 5-8: instruction-handler boundary detection (via Anchor IDL when present, discriminator-based fallback) + diffing between two binaries; days 9-11: CPI-target and account-check extraction/diff; days 12-14: plain-English summary renderer + CLI polish. Demo: take a real historical Solana program upgrade (a well-known protocol's two consecutive mainnet deployments) and run `upgrade-lens old.so new.so`, showing a signer-readable summary ("added CPI call to program X," "removed an owner check on account Y") in seconds, next to the current reality of a signer clicking "approve" with zero visibility into exactly that.
- **Track fit:** Solana ($100k/10) — direct hit; secondary relevance anywhere multisig-gated upgrades happen (most L2/Orbit chains too), but scoped and demoed as Solana-first.

No existing tool converts a binary-vs-binary sBPF diff into a signer-facing readable summary.
