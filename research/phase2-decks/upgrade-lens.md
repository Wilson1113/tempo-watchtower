# upgrade-lens — Pitch Deck (Candidate T3)

Track: Solana ($100k / 10 winners). Domain: VM/execution-runtime core infra + signer-facing cryptography/security. Working name kept: **upgrade-lens** (see naming note in §1). This deck supersedes Phase 1's VM-05 write-up with fresh verification as of 2026-09-25. **Two findings below (§8) materially update the whitespace picture from Phase 1 — a wider field of adjacent tools than Phase 1 found, but the specific bytecode/CPI-level gap this product targets is confirmed still open — flagged plainly rather than smoothed over.**

---

## 1. Title + one-liner

**upgrade-lens**
*A pure-Rust CLI/library that takes two sBPF ELF binaries — the currently-deployed Solana program and a pending upgrade buffer — and produces a structured, human-readable diff of exactly what changed (instruction handlers, CPI call targets, account-ownership/signer checks) in plain English, so a multisig signer can tell the difference between a routine upgrade and a trap in the 60 seconds before they click approve.*

**Naming note:** Kept **upgrade-lens** over Phase 1's alternate framing ("Solana Program Upgrade Diff-for-Humans" as description, not a proposed name). Fresh check this session (`crates.io` API, GitHub repository search): no existing Rust crate is named `upgrade-lens`, and no crypto/Solana project uses it — the string is used by ~16 unrelated repos (an Optimizely CMS migration analyzer, a Frappe ERP upgrade tool, several eyewear/camera-lens products), none in web3, so there is no confusing collision inside the relevant community. The name reads clearly to a Solana-native judge: "lens" signals inspection/visibility, "upgrade" signals the exact trigger event. One honest risk: the name doesn't communicate *multisig-signer-facing* scope on its own — the README's first line needs to say "for the person about to click Approve" immediately, the same disambiguation-on-first-line lesson from the sibling `simd-diff` deck.

## 2. Problem statement

**The gap, in one sentence:** A Solana multisig signer approving a program upgrade sees a buffer account and a program ID, not what actually changed in the code — and no tool converts a binary-vs-binary sBPF diff into a plain-English, signer-readable summary before they approve.

**Evidence:**

1. **VERIFIED (re-fetched fresh this session, 2026-09-25):** SEAL's (Security Alliance) Solana Wallet Security framework, secure-multisig-Squads-verification page — quote confirmed unchanged from Phase 1: **"Limited tooling is available for Solana verification compared to EVM. Exercise extra caution and cross-verify with team members."** A second line surfaced fresh this session on the same page, not quoted in Phase 1: **"Solana verification tooling is significantly less mature than EVM. There are no widely adopted equivalents to Safe CLI hash verification utilities or calldata decoders."** https://frameworks.securityalliance.org/wallet-security/signing-and-verification/secure-multisig-squads-verification/ — The page's actual coverage (re-confirmed) is SOL transfers, token transfers, and multisig config changes only; it does not address program-upgrade content review at all.
2. **VERIFIED (new this session):** Checked SEAL's full Wallet Security framework table of contents (12 sub-pages: wallet types, custody models, account abstraction, TEE wallets, smart-contract-interaction security, seed management, tools/resources, signing-and-verification). **None of the 12 sections addresses program-upgrade bytecode review** — the gap isn't a missing sub-page detail, it's absent from the framework's scope entirely. https://frameworks.securityalliance.org/wallet-security/
3. **INHERITED, downgraded to UNVERIFIED this session:** Phase 1 cited Squads/`solana-verify` docs (via WebSearch synthesis, already marked UNVERIFIED there) describing the recommended workflow as verifying "that the on-chain buffer matches the program source code using Ellipsis Labs's verifiable build." Fresh attempt this session to fetch a live Squads docs page (`docs.squads.so/main/security/verification`) **returned a 404** — the specific URL no longer resolves (if it ever did; this was never independently fetched). The underlying claim (authenticity-verification, not content-diffing, is the current best practice) is still corroborated independently via the GitHub evidence in #4 below, so the conclusion holds, but the original Squads-docs citation itself could not be re-verified and should be treated as unconfirmed.
4. **VERIFIED (new this session, GitHub):** The two closest first-party/official tools confirm the authenticity-only ceiling directly. `otter-sec/otter-verify` (OtterSec's own on-chain verification program, 26 stars) — its README states the tool's purpose is to "confirm that the deployed program... matches this repository" by "building the program in Docker and verifying that the computed hash matches the deployed program hash." `solana-foundation/squads-program-action` (Solana Foundation's own GitHub Action for Squads upgrades, pushed 2026-09-16) orchestrates buffer/IDL upload and an "Optional PDA verification instruction" via `solana-verify export-pda-tx` — again a hash/authenticity check, not a diff of what changed. Both confirm: even the most current, most official tooling in this exact space stops at "is this buffer what the source claims it is," never "what changed since the last deployed version, and is that changed thing dangerous." https://github.com/otter-sec/otter-verify · https://github.com/solana-foundation/squads-program-action
5. **VERIFIED (new this session, GitHub):** Two small, independent solo projects attempt upgrade-safety checking at the **IDL/schema level**, not the bytecode level, and both explicitly disclaim the exact capability this product targets. `saicharanpogul/ratchet` (1 star, last pushed 2026-07-30): diffs Anchor/Quasar/Codama IDL files for account-layout, discriminator, and instruction-signature changes; per its own scope note, it does **not** check "CPI call targets, account-ownership rules, or signer verification logic — those require runtime analysis beyond IDL scope." `FannBe/solana-upgrade-guard` (0 stars, single-day project, 2026-06-25, no activity since): diffs two Anchor IDLs for struct/account-layout compatibility and separately checks upgrade-authority custody (hot wallet vs. multisig); explicitly does not inspect "bytecode, CPI invocations, or permission logic." Both tools independently name the exact gap (CPI targets, account-ownership/signer-check content) this product fills — from the outside, by people who tried adjacent things and stopped short of it. https://github.com/saicharanpogul/ratchet · https://github.com/FannBe/solana-upgrade-guard

**Who exactly hits this, roughly how many, where they'd find this product:** Squads v4 multisig signers and DAO/protocol governance/security-council members who must approve a program-upgrade transaction without personally having written the diff — named because Squads' own security guidance calls out multisig program-upgrade approval as a distinct, high-stakes review step (INHERITED from Phase 1, corroborated indirectly this session by Solana Foundation's own investment in Squads-upgrade CI tooling, evidence #4). Gather on the Squads Discord, SEAL's own framework/community channels, and DAO governance forums (Realms). No hard population count exists (Phase 1 didn't produce one either) — the honest scope claim is "every team using Squads v4 program-upgrade authority," a large but uncounted set, not a specific number like VM-01's 17,332 SBPFv0 programs.

**Honest note on urgency framing:** Phase 1 tied this to SIMD-0500's forced-rebuild wave (see `simd-diff` deck) as a "shared demo narrative" — that every team rebuilding for SBPFv3 will need exactly this signer-review step. That link still holds structurally (a forced rebuild is itself a program-upgrade event needing signer approval), but SIMD-0500 itself is fresh-verified (see `simd-diff` §2) to still be at SIMD-process status `Idea` (not "Review" as Phase 1 stated) with mainnet activation timing unconfirmed — so the "urgent because of a dated deadline" framing should be presented as a *contributing* factor, not the core evidence. The core evidence (the SEAL gap-admission, the authenticity-only ceiling of every existing tool, the two IDL-level tools that explicitly stop short) stands independent of SIMD-0500's timeline and is not weakened by that correction.

## 3. What we are

**Ships as:**
- **`upgrade-lens`** — a Rust CLI (`cargo install upgrade-lens`) and library crate of the same name, so the diff engine can be embedded directly into a multisig platform's approval UI (see §5) rather than shelled out to.
- Core subcommand shape: `upgrade-lens diff <deployed.so> <buffer.so> [--idl <program.json>] [--format human|json]` — takes the two ELF binaries directly (fetched by the caller via RPC from the program-data account and the pending buffer account, or supplied as local files), and emits either a plain-English report for a terminal/UI or structured JSON for programmatic embedding.

**Core technical mechanism:**

1. **ELF loading and sBPF disassembly.** Both binaries are loaded and disassembled using Anza's actively-maintained `solana-sbpf` crate (`anza-xyz/sbpf`, confirmed fresh this session on crates.io at v0.25.0) — **a correction to Phase 1's citation**, which referenced `solana_rbpf`; that name still exists on crates.io but is stalled at v0.8.5 and is the predecessor/legacy name for the same VM+JIT project, now published as `solana-sbpf`. Using the actively-maintained crate matters directly for this product: it tracks the SBPFv0→v3 ELF-format changes (`e_machine` field changes, etc.) that are already causing real breakage elsewhere in the ecosystem (the `anchor-litesvm` issue #3 parser mismatch documented in the `simd-diff` deck) — a diff tool built on a stale disassembly dependency would misparse exactly the newest upgrades it most needs to handle correctly.
2. **CFG extraction.** A control-flow-graph pass over each binary's disassembly identifies function/basic-block boundaries — the structural backbone both the instruction-handler-boundary detection and the CPI/account-check extraction (steps 3-4) are built on.
3. **Instruction-handler-boundary detection, with fallback.** When an Anchor IDL is available (common — Solana Foundation's own `squads-program-action`/`github-actions` tooling already uploads IDLs alongside program upgrades as standard practice, confirmed fresh this session), instruction handlers are matched by their 8-byte Anchor discriminator directly to IDL-named instructions — giving named, human-readable handler identity for free. When no IDL is available (native programs, or IDL upload skipped), handlers are identified from CFG entry points reachable from the program's dispatch/`process_instruction` switch, keyed by raw discriminator bytes instead of names — a strictly weaker but still diffable identity.
4. **CPI-target diffing.** Within each identified handler's CFG, calls to the `sol_invoke_signed`/CPI syscall are located, and the invoked program ID — whether a compile-time constant or a runtime-resolved account reference — is extracted per call site. The set of CPI targets per handler is diffed old-vs-new: an added call to an unfamiliar program ID inside a previously CPI-free handler is exactly the "a malicious added call" signal a signer cannot currently see (§2, evidence #4-5: no existing tool, including the two IDL-level ones, reaches this layer at all).
5. **Account-ownership/signer-check diffing.** Within each handler's CFG, patterns matching account-metadata checks (`is_signer`, `owner ==`, discriminator/type checks against expected account structs) are pattern-matched from the basic blocks immediately following account deserialization. Removed or weakened checks (a signer check present in the old binary, absent at the equivalent CFG position in the new one) are flagged explicitly — the other half of the "malicious or buggy upgrade" signal a signer needs, and again a layer both `ratchet` and `solana-upgrade-guard` explicitly disclaim (§2, evidence #5).
6. **Plain-English summary renderer.** The structured diff (added/removed/changed handlers; added/removed CPI targets per handler; added/removed/weakened account checks per handler) is rendered as short natural-language lines — "added CPI call to program `<pubkey>` inside handler `withdraw`," "removed owner check on account `vault` inside handler `close_position`" — the signer-facing artifact this whole product exists to produce; the structured JSON underneath is what a multisig platform's UI would consume directly (§5).
7. **Why pure Rust, not a web dApp:** the entire mechanism is ELF parsing, sBPF disassembly, and CFG analysis on binary bytes — this is systems-programming work with zero end-user-facing surface of its own to wrap in a UI; the actual UI is someone else's approval screen (Squads', Realms', or a terminal). Building the core engine in anything but Rust would mean either re-implementing sBPF decode semantics from scratch or FFI-wrapping `solana-sbpf` (itself Rust) from another language, adding a correctness boundary in exactly the place a security tool can least afford one — a wrong parse is a false "no CPI change" on a binary that actually added one.

**Who's building this:** solo builder, hackathon submission for Colosseum's Crypto World's Fair.

## 4. Tech demo (3-minute plan, minute-by-minute)

**Honest gap flagged up front, same as the sibling `simd-diff` deck:** this research pass did not pre-identify a *specific named pair* of consecutive real mainnet deployments to use in the demo — finding one is a concrete first-build-day task, not yet done. The most reliable sourcing method identified this session: use `solana-verify build` (the same Ellipsis Labs / OtterSec verifiable-build toolchain the ecosystem already trusts for authenticity checks, confirmed live and current via evidence in §2/§8) to reproducibly rebuild a well-known **open-source** Anchor program at two consecutive git tags corresponding to two real mainnet upgrades — Squads' own v4 program is itself open-source with a tagged release history and would make an apt, if slightly self-referential, choice ("we diffed the diffing tool's own signer's tool"); alternatives with public source and multiple mainnet upgrades (Marinade, Drift, Kamino, Jupiter) are equally viable and should be evaluated on day 1 for which has the cleanest, most legible single-upgrade diff for a 3-minute audience. A third-party verified-build registry (`DeployDAO/solana-program-registry`, 40 stars, confirmed this session to build and host binaries keyed by git tag) is a possible shortcut if it already covers the chosen program, but its actual program coverage could not be confirmed from the README alone this session — local rebuild via `solana-verify` is the fallback that doesn't depend on that being true.

- **0:00–0:20 — Cold open, stakes.** Screen: a real Squads (or Realms) approval screen showing a pending program-upgrade transaction — buffer account, program ID, "Approve" button — and nothing else. Voiceover: "This is what a signer sees. This is what they're trusting."
- **0:20–0:45 — Name the gap, on-screen citation.** Cut to SEAL's framework page, the exact quote from §2 evidence #1-2 highlighted: "Limited tooling is available for Solana verification compared to EVM." One line: "The security community's own framework admits this. Nobody has shipped the fix."
- **0:45–1:15 — Run the tool.** Terminal: `upgrade-lens diff old.so new.so --format human` against the two real rebuilt binaries from the chosen protocol's consecutive mainnet upgrade. Output streams in seconds.
- **1:15–2:15 — Read the output like a signer would.** Walk through 2-3 concrete lines the tool actually produced: e.g., "added CPI call to program `<pubkey>`" (pause: "is that a program you recognize? Would you have caught this by reading a buffer address?"), "removed owner check on account `<name>`" (pause: "this is the exact class of bug that turns a routine upgrade into a fund-loss event"). If the chosen real historical upgrade is genuinely benign (likely, for a reputable protocol), supplement with one deliberately-reintroduced bug on a forked copy to show the tool catching an actual dangerous change, clearly labeled as staged.
- **2:15–2:45 — Zoom out.** Split screen: signer's current reality (buffer address, blind approve) vs. upgrade-lens's plain-English report, side-by-side. One line: "This is the Bybit blind-signing story, but for the code itself, not the transaction."
- **2:45–3:00 — Close.** OSS CLI today; the B2B pitch (embed this directly in Squads'/Realms' approval UI) in one line, into §5.

## 5. Business model

**Who pays, how, realistic pricing:**
- **Free, open-source CLI/library** for individual developers, security researchers, and any signer willing to run a terminal command before approving — this is also the Public Goods Award-eligible layer (adoption, trust, and the baseline the paid tier builds on).
- **Paid B2B API/embedding license** for multisig platforms (Squads) and governance tooling (Realms) to integrate the diff-and-summary output directly into their own approval UI, so a signer sees "added CPI call to program X" inline on the approval screen itself, with zero CLI step required. Realistic pricing model: a per-program or per-organization API license fee, priced like other embedded security-tooling integrations (e.g., OpenZeppelin Defender's Sentinels, Tenderly's alerting add-ons) rather than a per-seat SaaS — the buyer is the platform, not the individual signer.
- **Secondary channel, not primary:** consulting/integration engagements with individual DAOs or protocol security councils that want the diff wired into their specific upgrade-governance pipeline (a Snapshot/Realms proposal that must attach a signed diff report before a vote opens, for instance).

**Applying the 4-point niche filter explicitly:**
1. **Named, reachable users:** Squads v4 multisig signers and DAO/protocol governance/security-council members — a real, named population gathering on Squads' own Discord and Solana governance forums, confirmed via Squads' own security messaging calling out this exact review step (§2).
2. **Real cost, not annoyance:** the cost this product avoids is a signer approving a **malicious or buggy program upgrade** — direct, catastrophic fund loss, the exact structural analog of the Bybit blind-signing hack ($1.5B, Feb 2025) that framed this entire research effort, except at the program-bytecode layer instead of the transaction layer. This is not "saves a signer some reading time" — it is "prevents the single most catastrophic failure mode a multisig-governed protocol has: its own signers unknowingly authorizing the theft of the funds they're supposed to protect." A protocol or DAO treasury holding tens or hundreds of millions of dollars has a direct, quantifiable incentive to prevent exactly this, distinct from any mere developer-convenience tool.
3. **Structural, not circumstantial, incumbent neglect:** re-confirmed this session (§2 evidence #4) that even the two most current, most official adjacent tools — OtterSec's own `otter-verify` and Solana Foundation's own `squads-program-action` — stop at buffer-authenticity (does this match the claimed source), never content-diffing (what changed, and is it dangerous). The sharper structural point, refined this session: authenticity-verification is infrastructure/commodity work audit firms and foundations are happy to give away (it's table-stakes, low-differentiation, good marketing) — but the *judgment layer* (reading a diff and deciding whether a change is a risk) is exactly the billable expertise OtterSec/Zellic/Sec3 sell as manual audit work, and is structurally the part they have the least incentive to automate away for free.
4. **Enjoyable domain work:** ELF/sBPF disassembly, CFG extraction, and pattern-matching account-check logic out of a control-flow graph is genuinely deep VM-internals and cryptography-adjacent systems work — not applied plumbing.

## 7. Track fit & judging-criteria mapping

- **(a) Functionality:** A working CLI that takes two real ELF binaries and produces a genuinely correct CPI-target and account-check diff is a hard, demonstrable, verifiable-on-the-spot capability — judges can hand the tool an arbitrary program pair and see if it's right.
- **(b) Potential Impact:** TAM is every Squads-governed treasury and every DAO/protocol with multisig-gated program-upgrade authority on Solana — a large, if uncounted, population (§2) — and the downside prevented (a single successful malicious-upgrade approval) is unbounded relative to the tool's cost, mirroring exactly the asymmetry that made the Bybit hack a watershed event.
- **(c) Novelty:** Fresh-confirmed this session: no existing tool operates at the bytecode/CPI-target/account-check layer for upgrade diffing — the two closest attempts (`ratchet`, `solana-upgrade-guard`) explicitly stop at IDL/schema level and disclaim exactly this capability (§2, §8). The concept — decompile-enough-to-diff-meaningfully, rendered in plain English for a non-engineer signer — has no packaged precedent found.
- **(d) UX:** The entire pitch is a UX story: the blockchain gives signers a cryptographically-verifiable buffer account and nothing else legible; this tool is the translation layer between "trustworthy but illegible" on-chain data and a decision a human can actually make in 60 seconds — directly answering "how well does this use blockchain to create great UX for downstream users."
- **(e) Open-source:** OSS CLI/library by default (§5); composes with Squads and Realms as an embeddable primitive rather than a closed competing product — the B2B model is a license on top of open code, not a proprietary fork.
- **(f) Business Plan:** A believable, distinctly B2B-not-B2C model (§5) — the platforms pay, not individual signers — with a free-tier-drives-adoption-then-license-the-integration path that has real precedent in adjacent security tooling (OpenZeppelin Defender, Tenderly).

**Honest note on track crowding:** Solana is very likely the single most-submitted track in this hackathon — it is Colosseum's home ecosystem and the track most Solana-native builders will default to, though this session could not pull hard submission-count data (the Colosseum project gallery remains JS-rendered and unenumerable via WebFetch, same limitation Phase 1 hit). Given that, the case for standing out inside a crowded Solana track specifically is: (1) this is a **signer-facing security tool**, not another dApp/DeFi primitive or dev-infra utility — a different judging lens (UX-for-a-decision, not UX-for-a-transaction); (2) the specific bytecode/CPI-diff mechanism is fresh-confirmed unclaimed even after a wider competitor search than Phase 1 ran (§8); (3) it demos crisply and legibly to non-Solana-expert judges (a plain-English line is instantly understandable in a way "CU regression" or "SIMD compliance" is not).

**Re-checking the audit-firm-neglect argument, fresh, honestly:** the argument holds, refined rather than weakened. Fresh evidence (§2 #4) shows OtterSec *does* build and give away free infrastructure (`otter-verify`, authenticity-checking) — so the naive claim "audit firms never give anything away free" would have been overclaiming, and Phase 1's framing risked exactly that overclaim. The more precise and now better-evidenced claim: audit firms give away *commoditized, low-judgment* infrastructure (build reproducibility, hash matching) because it's cheap to build, good marketing, and doesn't compete with their revenue — but the *judgment layer* (is this specific diff dangerous) is their actual billable product, and no audit firm has shipped a free tool at that layer. **Does this cut against adoption?** Partially, and this should be said plainly: an audit firm could plausibly react to this tool's traction by (a) building a fancier version themselves as a lead-generation/marketing play once demand is proven — a real threat, not hypothetical, given OtterSec already ships adjacent free infra — or (b) simply not caring, since a self-serve tool for *every* upgrade doesn't replace the deep manual audit engagement a serious protocol still buys before a major upgrade; the two products (continuous lightweight signer-facing diffing vs. periodic deep audits) plausibly coexist rather than compete. The honest risk to flag for judges/investors: this product's moat is thin against a well-resourced audit firm deciding to build the same thing and give it away to build their brand — the defensible position is being first, being genuinely embedded in Squads'/Realms' UI (a distribution moat, not a technical one), not any durable technical secret.

## 8. Competitive scan (for the verifier)

Being the harshest available critic of this idea's whitespace claim:

- **`otter-sec/otter-verify`** (OtterSec, 26 stars) — https://github.com/otter-sec/otter-verify — On-chain program + tooling confirming a deployed binary's hash matches a claimed source repo. **Does not diff two versions or summarize content changes** — pure authenticity check. Built by an actual audit firm, which is the strongest single data point for §7's "would audit firms build this themselves" risk.
- **`solana-foundation/squads-program-action`** (Solana Foundation, 3 stars, pushed 2026-09-16) — https://github.com/solana-foundation/squads-program-action — Official GitHub Action orchestrating Squads program-upgrade transactions plus optional PDA/authenticity verification. **No content diffing.** Its existence, alongside sibling repos `solana-foundation/github-actions` (12 stars, pushed 2026-09-16) and `solana-foundation/github-workflows` (26 stars, pushed 2026-08-04), shows Solana Foundation is actively investing in Squads-upgrade CI tooling *right now* — a real, fresh update to Phase 1's "big players won't do it" framing: they are doing *adjacent* infrastructure work, just not this specific diff layer, and could plausibly extend into it faster than Phase 1 assumed.
- **`saicharanpogul/ratchet`** (1 star, last pushed 2026-07-30, stale ~2 months) — https://github.com/saicharanpogul/ratchet — The single closest positioned competitor found. Diffs Anchor/Quasar/Codama IDL files (27 rules: account-layout, discriminators, instruction signatures, PDA seeds) and explicitly targets both developers pre-deploy *and* "multisig signers reviewing pending upgrades" — the same audience this product targets. **Explicitly disclaims** CPI-target and account-ownership/signer-check diffing as "runtime analysis beyond IDL scope." Also operates on the *claimed* IDL, not the compiled binary directly — meaning it trusts that the IDL accurately describes the deployed bytecode, an assumption upgrade-lens's binary-first approach doesn't need. Low traction (1 star, stale) suggests either low current demand or low current visibility — ambiguous which.
- **`FannBe/solana-upgrade-guard`** (0 stars, single-day project, 2026-06-25, no activity since) — https://github.com/FannBe/solana-upgrade-guard — Diffs two Anchor IDLs for account-layout compatibility; separately checks upgrade-authority custody (hot wallet vs. multisig/immutable). **Explicitly excludes** bytecode, CPI invocations, and permission logic. Appears to be an abandoned hackathon-style submission, not an active project.
- **`illegalcall/sbpf-analyzer`** (crates.io: "Static compute unit analyzer for Solana sBPF bytecode") — bytecode-level sBPF tooling exists and is packaged as a crate, confirming the underlying disassembly work is tractable at the crate-ecosystem level, but the analysis target is CU cost, not diffing or CPI/account-check extraction. Adjacent prior art, not a competitor.
- **`SpriteDay/sbpf-decompiler`** (0 stars, last pushed 2026-09-12, confirmed unchanged from Phase 1) — https://github.com/SpriteDay/sbpf-decompiler — "App suite for full sBPF decompilation back to Rust code." Decompiles one binary; **no diffing capability** in the README. Monorepo with a real disassembler crate inside it — a possible dependency or reference implementation, not a competing product.
- **`owizdom/SBPF-3-1`** (0 stars, stale since 2026-01-06, confirmed unchanged from Phase 1) — "a toolkit for analyzing and decompiling SBPF binaries." Same story: single-binary analysis, no diff feature evident.
- **`QEDGen/qedsvm`** (new find this session, created/pushed 2026-09-25 — today) — "Execute and verify compiled Solana sBPF programs with a Lean 4 reference model." Formal-verification of VM execution *semantics* against a Lean4 spec — a different problem (does the VM execute correctly) from this product's problem (did the program's *content* change dangerously between two versions). Not a competitor, but worth watching as evidence the sBPF-tooling space is getting fresh, serious attention exactly now.
- **Crates.io check (fresh this session):** no crate named `upgrade-lens`, `solana-diff`, or equivalent exists; `sbpf-coverage` ("Maps SBPF execution traces to source code for test coverage") is the closest adjacent crate using similar CFG-to-source mapping technique, but for test coverage, not diffing.

**Harshest-critic summary:** Phase 1's claim of "near-total absence of any packaged competitor" was accurate for the *specific bytecode/CPI-diff* mechanism but understated how much adjacent activity exists one layer up (IDL-level diffing: 2 tools; authenticity verification: increasingly official/first-party). The whitespace this product actually owns, re-confirmed after a wider search: **binary-level CPI-target diffing and account-check diffing, rendered as a plain-English signer-facing summary.** That specific combination remains unclaimed. The risk is that it is unclaimed partly because it is harder (real decompilation-adjacent work, not IDL parsing) — which cuts both ways: harder to build (a solo-14-day-MVP risk) but also harder for a fast-follow competitor to replicate cheaply.
