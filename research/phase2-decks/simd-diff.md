# simd-diff — Pitch Deck (Candidate #3)

Track: Solana ($100k / 10 winners). Domain: VM/execution-runtime core infra. Working name kept: **simd-diff** (see naming note in §1). This deck supersedes Phase 1's VM-01 write-up with fresh verification as of 2026-09-25 — **one finding below (§8, UpgradeGuard) materially changes the whitespace picture from Phase 1 and is flagged prominently rather than smoothed over, per instructions.**

---

## 1. Title + one-liner

**simd-diff**
*A Rust CLI + library that replays a program's real recent mainnet traffic against its current and candidate SBPFv3 binaries side-by-side, diffs the logs/CU/state, and statically flags the exact footguns that make a "successful" rebuild silently break at runtime — built so the 17,000+ programs facing Solana's SIMD-0500 forced migration don't have to redeploy and pray.*

**Naming note:** Kept **simd-diff** over alternatives. "redeploy-radar" (VM-01's alternate) undersells the binary-diff mechanism and oversells "radar/scanning," which is closer to what a fleet-wide scanner (a different, rejected candidate idea, C3/sbpf-fleet) does. A generic "sbpf-replay" is more literal but loses the direct tie to the *named, dated* SIMD numbers (0500, 0459, 0460) that are the whole evidentiary spine of this pitch and read as fluent to Solana-native judges. One honest naming risk worth flagging: `crates.io` has zero existing crates named `simd-diff` (VERIFIED, checked fresh this session), but a developer skimming crates.io could momentarily read "SIMD" as CPU SIMD instructions (a very common Rust-ecosystem meaning) rather than Solana's SIMD governance-proposal numbering — the README's first line needs to disambiguate immediately. Also worth noting: the closest live competitor (see §8) is called **UpgradeGuard**, not anything SIMD-prefixed, so there's no direct name collision — but it is functionally the more urgent naming/positioning problem, not the string itself.

## 2. Problem statement

**The gap, in one sentence:** Solana's SIMD-0500 will make SBPFv3 the only deployable bytecode format, forcing a mandatory rebuild-and-redeploy of thousands of already-live programs — and today, a developer who rebuilds their program has no way to ask "will replaying my program's actual recent mainnet traffic against this new binary produce the same logs, CU cost, and account state?" before they redeploy for real.

**Evidence:**

1. **VERIFIED (re-fetched fresh this session, raw file, 2026-09-25):** SIMD-0500's own frontmatter and body, from `github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0500-disable-deployment-of-sbpf-v0-v1-v2.md`: mainnet loader-v3 (upgradeable) program counts are **"17279 [SBPFv0], 12 [SBPFv1], 41 [SBPFv2]"** — 17,332 total, unchanged from Phase 1's citation. The detailed design section: after activation, `DeployWithMaxDataLen`, `Upgrade`, and `SetAuthority`/`SetAuthorityChecked`-to-no-authority (finalization/freezing) on any pre-v3 ELF "must return `InstructionError::InvalidAccountData`" — confirming both the redeploy-block *and* the freeze-block Phase 1 cited. **Correction to Phase 1:** Phase 1's VM-01 stated SIMD-0500's status was "Review" at research time. Fetching the raw file directly this session shows the frontmatter reads **`status: Idea`**, unchanged since the proposal was merged into the repo on 2026-04-22 (VERIFIED via GitHub API commit history — one commit, no subsequent status edits) and `feature: TBD`. This is five months with no formal status advancement in the SIMD process itself (Idea → Draft → Review → Accepted → Implemented) — a real, honest downgrade from Phase 1's framing, not just a nitpick.
2. **VERIFIED (new this session, GitHub API):** The gap between "SIMD doc still says Idea" and "this is actually happening" is resolved by checking the *implementation*, not just the proposal doc: Agave PR [#10880](https://github.com/anza-xyz/agave/pull/10880), "Feature - Disable SBPF v0, v1 and v2 deployment," was **merged into `anza-xyz/agave` master on 2026-05-01**, keying the feature `disable_sbpf_v0_v1_v2_deployment` and linking a feature-gate-tracker issue (`anza-xyz/feature-gate-tracker#346`) for cluster activation scheduling. That tracker repo returned 404 on both the GitHub API and web fetch this session (likely private/internal) — so **the actual mainnet activation epoch cannot be independently verified from a public source**; this is an honest gap, not a confirmed date. What *is* confirmed: the code exists and has existed in Agave master for ~4.5 months; only the on-chain activation timing is unconfirmed.
3. **VERIFIED (new this session):** Agave's own release history (`api.github.com/repos/anza-xyz/agave/releases`) shows **v4.3.0 went stable on 2026-09-18**, and **v4.4.0-alpha.5 was cut the same day**, explicitly labeled "pre-release for testing only. Do not deploy to mainnet, testnet, or any production host." There is no stable v4.4 yet as of this research. This is consistent with — but does not itself prove — Anza's "~Nov 2026" v4.4 target cited by Phase 1 and by hackathon-intel's Section C; treat the Nov 2026 date as **plausible given release cadence, still UNVERIFIED as a hard date** from any Anza source fetched this session.
4. **VERIFIED (re-fetched fresh, Anza migration blog, `anza.xyz/blog/migrating-solana-programs-to-sbpfv3`):** "Don't wait for an activation date. Migrate now." Exact quote on the footgun: *"If you're using `extern "C"` declarations instead of `define_syscall!`, unresolved symbols will remain in your bytecode as `call -1`. When executed, this causes your program to loop until reaching the maximum instruction frame limit, returning a `CallDepthExceeded` error."* The blog explicitly recommends testing with **"Mollusk, LiteSVM, Surfpool, or Anchor before deployment"** — i.e., Anza's own guidance names the exact category of tool this product is, without Anza building or endorsing one specific tool that does it end-to-end. This is the strongest "why big players won't do it" evidence: the protocol team tells you *what* to test with, not *how* to automate testing your specific deployed program's specific traffic.
5. **VERIFIED (new this session, live and current):** `anchor-litesvm` issue [#3](https://github.com/brimigs/anchor-litesvm/issues/3) remains **open**, no maintainer fix merged, as of this session. Confirmed root cause: `sbpf` 0.13.1's strict ELF parser (pulled in via `litesvm` 0.11.0 / Agave 3.1.x) requires `e_machine == EM_SBPF (263)`, but platform-tools v1.57's finalized SBPFv3 target emits `e_machine == EM_BPF (247)` — a real, current, in-the-wild example of exactly the "binary that should replay correctly doesn't, because the test harness's own dependency chain is stale" failure mode this product has to guard against in its own build (fix: pin `litesvm >= 0.16.0`, confirmed released 2026-08-24, which uses `sbpf >= 0.14.4`).
6. **VERIFIED (new this session):** Surfpool's `profile` PR [#786](https://github.com/solana-foundation/surfpool/pull/786) — the closest first-party-adjacent tool — is **still open, unmerged, last activity 2026-09-14**, unchanged from Phase 1. A reviewer bot's flag stands unresolved: replaying a historical transaction executes it "under runtime rules that were not active at its original slot, causing misleading errors." It also still has **no binary-override capability** — it profiles the currently-deployed program only, never a candidate rebuild. Surfpool itself is a large, actively developed project (602 stars, pushed 2026-09-24) — but this specific gap is unchanged.

**Who exactly hits this, roughly how many, where they'd find this product:** Solana program upgrade authorities and maintainers of long-tail programs deployed in 2023-2024 that haven't touched their toolchain since — "token launches from 2023/2024 with a custom program, NFT projects, small DeFi protocols, games" per xroot.dev's framing (inherited from Phase 1, not re-fetched this session). Nominal population: **17,332 upgradeable mainnet programs still on SBPFv0/v1/v2** (VERIFIED fresh, above). **Honest caveat, not in Phase 1:** a competing hackathon team's own research (see §8) independently concluded the *economically relevant* subset — active, source-available, team-present, expecting future upgrades — is meaningfully smaller than 17,332; neither that team nor this research has a hard number for the addressable subset, and inflating "17,332" into "17,332 customers" would overclaim. The honest claim is: 17,332 is the ceiling, not the market size. They gather on Solana Stack Exchange, the Solana Tech Discord `#dev-support` channel, and Anza/Firedancer GitHub — these three venues are inherited from Phase 1 and were not independently re-verified this session (mark UNVERIFIED as gathering-venue claims specifically, though plausible).

## 3. What we are

**Ships as:**
- **`simd-diff`** — a Rust CLI (`cargo install simd-diff`) and a library crate with the same name, so the replay-and-diff engine can be embedded in another team's CI pipeline directly rather than shelled out to.
- Core subcommands: `simd-diff fetch <program_id> --recent N` (pull N real recent signatures/transactions touching the program via RPC), `simd-diff lint <candidate.so>` (static footgun pass, no network needed), `simd-diff replay <program_id> --candidate <candidate.so> [--baseline mainnet|<baseline.so>] [--feature-set mainnet|<slot>]` (the core replay-and-diff), producing a JSON report (for CI) or a human-readable table (for terminal use), with a non-zero exit code on any divergence — so it composes as a CI gate, not just an interactive tool.

**Core technical mechanism — specific, built on LiteSVM's confirmed current API (checked fresh this session against `docs.rs/litesvm/latest`, crate version 0.16.0, released 2026-08-24):**

1. **Fetch real traffic, not hand-written fixtures.** `simd-diff fetch` calls RPC `getSignaturesForAddress` against the target program, pulls the last N transactions, and for each one resolves every account it touches (`getMultipleAccounts` / `getTransaction`) — the program's own executable/programdata account plus every account in the transaction's account-keys list. This is the deliberate point of difference from the closest competing tool (see §8): nobody has to *know in advance* what to test. This matters most for exactly the long-tail, abandoned-or-thin-team programs this pitch targets, where no one is available to hand-author a fixture file.
2. **Two isolated LiteSVM instances, one binary each.** Baseline instance loads the currently-deployed program bytecode via `add_program_with_loader(program_id, baseline_bytes, loader_id)` (matches mainnet CU accounting per LiteSVM's own docs — "Adds an SBF program with a specific loader to match mainnet CU behavior"); candidate instance loads the rebuilt/upgraded binary the same way. Every fetched real account (step 1) is hydrated into **both** instances via `set_account(address, account)`, so both replays start from an identical, real, mainnet-derived state — not a synthetic fixture.
3. **Pin the feature set identically across both runs.** Both instances call `.with_feature_set(FeatureSet)` — either `LiteSVM::mainnet_feature_set()` / `.with_mainnet_features()` for "what does this look like today," or an explicit feature set with SIMD-0459/0460/0500's gates flipped on, for "what does this look like after the upgrade." Pinning both sides identically is a deliberate design response to Surfpool PR #786's still-open correctness bug (item 6, §2) — replaying a transaction under a feature set that wasn't active at its original slot is exactly the failure mode we design around by making both sides consistent and by exposing the feature-set choice explicitly in the CLI rather than hiding it.
4. **Replay and diff.** Each fetched transaction is sent via `send_transaction` (or `simulate_transaction` for a dry run) against both instances. The diff surface is LiteSVM's own `TransactionMetadata` struct (confirmed fields: `signature`, `logs: Vec<String>`, `inner_instructions`, `compute_units_consumed: u64`, `return_data`, `fee`) compared field-by-field, plus post-execution account state via `get_account(address)` on every account either run touched — catching state divergence, not just log/CU divergence.
5. **Static footgun linter, no replay needed.** Before (or independent of) any replay, `simd-diff lint` parses the candidate ELF header directly (`e_flags`/`e_machine`) and disassembles it to check for: (a) unresolved-syscall `call -1` patterns — the exact `extern "C"` footgun Anza's own blog warns about (item 4, §2); and (b) absolute-stack-address-dependent instruction patterns flagged by SIMD-0459/SIMD-0460 (Anza's own SIMD-0460 text: removing stack-frame gaps "can affect programs which rely on the address space layout of the stack" — a CFG-level heuristic similar in spirit to VM-05's sBPF diffing approach from Phase 1). **This second check is a confirmed, verified gap in the closest competing tool** — see §8.
6. **Why pure Rust, not a web dApp:** the entire mechanism is: load two ELF binaries into a Rust VM (LiteSVM literally is Rust), talk to Solana RPC, and diff Rust structs. There is no end-user-facing product surface to wrap in a UI — the customer is a developer's terminal or CI pipeline. Building this in anything other than Rust would mean either re-implementing SBPF execution semantics from scratch (pointless — LiteSVM/solana-svm already are the reference Rust implementation) or FFI-wrapping the Rust runtime from another language, which adds a correctness-risk boundary in exactly the place correctness matters most.

**Who's building this:** solo builder, hackathon submission for Colosseum's Crypto World's Fair.

## 4. Tech demo (3-minute plan, minute-by-minute)

**Honest gap flagged up front:** this research pass did not identify a *specific named* currently-SBPFv0, still-upgradeable mainnet program to use in the demo (Phase 1 didn't either — it said "pick a real... program" generically). Finding one is a concrete, executable first-build-day task: `getProgramAccounts` filtered to loader-v3-owned executables, cross-checked against ELF `e_flags`, exactly the query UpgradeGuard's own `scan`/`census` commands already perform (see §8) — a real program exists to find, but it is not pre-identified here. Budget time on day 1 for this, not during demo scripting.

- **0:00–0:20 — Cold open, stakes.** Screen: the SIMD-0500 proposal text (17,332-program table) side-by-side with Agave's release page showing v4.4.0-alpha.5 already cut (2026-09-18) — this is not hypothetical, the code for the block is already in an alpha build today.
- **0:20–0:50 — Discover a real target.** Run `simd-diff fetch <PROGRAM_ID> --recent 20` against a real, chosen-in-advance, still-SBPFv0, upgradeable mainnet program with genuine recent traffic. Show the terminal output: 20 real signatures pulled, accounts resolved.
- **0:50–1:30 — Build the candidate, with a deliberate bug.** Cut to a pre-prepared branch: the program rebuilt against the SBPFv3 toolchain, but with one `define_syscall!` call swapped back to a bare `extern "C"` declaration — reproducing the exact `call -1` footgun from Anza's own blog.
- **1:30–1:50 — Catch it statically, before any replay.** `simd-diff lint candidate.so` — flags the unresolved syscall immediately, quoting the SIMD-0178 rule it violates. This is the "would have caught it in seconds, for free, no RPC calls" moment.
- **1:50–2:30 — Catch it dynamically, against real traffic.** `simd-diff replay <PROGRAM_ID> --candidate candidate.so --feature-set mainnet` — replays the 20 real fetched transactions against baseline vs. candidate in two LiteSVM instances. Report shows: baseline all green; candidate transactions that hit the buggy code path return `CallDepthExceeded` and a CU spike, side-by-side, with exit code 1.
- **2:30–2:50 — Fix and re-run.** Restore `define_syscall!`, rebuild, re-run `simd-diff replay` — report goes green, CU delta reported (ideally near-zero, demonstrating a clean migration).
- **2:50–3:00 — Close.** One slide: `cargo install simd-diff`, the one-liner, repo link.

**Demo risk to flag honestly:** reliably reproducing a *specific* CU regression or `CallDepthExceeded` on real fetched mainnet transactions (rather than a synthetic worst case) depends on the chosen program's real traffic actually exercising the buggy code path — this needs real testnet/devnet rehearsal time before the demo is filmed, not just build time, mirroring the caution Phase 1 flagged for VM-02's demo.

## 5. Business model

**Who pays, how, and why this maps to "viable business":**

- **Free tier (adoption + Open-source judging criterion):** the `simd-diff` CLI and library crate, OSS (MIT/Apache-2.0), free for any individual developer or long-tail program owner — this is also the segment least able to pay, and the one the whole pitch is evidenced around, so a free tier isn't just goodwill, it's the only viable price point for the named 17,332-program population.
- **Paid tier (the actual business):** a hosted CI service — "pre-upgrade replay report as a service" — for protocols/DAOs that want `simd-diff` wired into their upgrade-PR pipeline automatically, gating merges on a clean replay-diff report, priced like existing security-tooling SaaS (Tenderly, OpenZeppelin Defender-style per-project/month pricing).
- **Channel:** audit firms (OtterSec, Zellic, Sec3) already do exactly this kind of pre-upgrade regression check by hand as billable work; a self-serve tool they can point clients at (or resell/white-label) is a plausible channel rather than a competitor to their billable work, since the manual, bespoke parts of an audit remain theirs.
- **New this session — an external pricing anchor, from a source that should be read skeptically since it is a competitor's own unvalidated hypothesis (see §8):** UpgradeGuard's internal planning document proposes near-identical tiers for the same problem — "Pro US$99–199/mo," "Enterprise US$1,000–5,000+/mo" — explicitly labeled by its own authors as an untested hypothesis, not a forecast. This is useful only as a directional signal that a second, independently-arrived-at team converged on similar price points for the same niche; it is not independent validation that anyone will actually pay this.

## 7. Track fit & judging-criteria mapping

Per the brief's verbatim rules §8, mapped one line each:

- **(a) Functionality:** A working replay-and-diff CLI against real fetched mainnet transactions, plus a static linter, is directly demoable and testable — code quality is judgeable by whether the reported CU/log/state diffs are actually correct, which the demo makes falsifiable on camera.
- **(b) Potential Impact:** TAM ceiling is a VERIFIED, named, protocol-level number — 17,332 upgradeable mainnet programs — with the honest caveat (§2) that the *addressable* subset is smaller and currently unquantified by anyone, including this research.
- **(c) Novelty:** Genuinely novel in combining three things nobody else combines yet (see §8): auto-fetched real-tx replay, binary-swap diffing, and SIMD-0459/0460-aware static analysis in one tool — but novelty has visibly narrowed in the days since Phase 1 (§8), and this should be stated plainly to the judges as a live, moving target, not claimed as settled whitespace.
- **(d) UX ("how well does this utilize blockchain to create great UX for downstream users"):** Weakest-fitting criterion of the six for this idea — this is a dev-tool for program authors, not an end-user-facing blockchain UX improvement; the honest answer is it improves UX *indirectly*, by preventing a broken redeploy from ever reaching the end users of the affected program.
- **(e) Open-source:** Ships fully OSS by design (free CLI/library is the whole adoption strategy, §5); composes directly with LiteSVM/solana-svm, Agave's toolchain, and could plug into `solana-verify`'s reproducible-build pipeline as an input.
- **(f) Business Plan:** A believable free-OSS-plus-paid-CI-service shape with a named, plausible channel (audit firms) and an (unvalidated, competitor-sourced) pricing anchor — see §5's honesty caveat on that anchor.

**On track crowding:** hackathon-intel's own Section D assessment is that Solana is **"most crowded"** overall — Colosseum's home turf, 1,000-2,900+ submissions in prior Solana-only hackathons, every generic app category saturated. This sub-niche (SIMD-0500/SBPFv3 migration tooling) was thin at Phase 1 research time specifically *because* it's unglamorous, dated, and requires understanding a specific protocol change most consumer-app builders never look at. **That thinness has narrowed materially in the ~24 hours before this session** (§8) — the honest framing for judges is "we found and built for a real, dated, protocol-level gap that a second, independent team converged on almost simultaneously, which is itself evidence the problem is real," not "we are the only team who thought of this."

## 8. Competitive scan (for the verifier)

**This section's most important finding, stated plainly and not smoothed over: the whitespace picture from Phase 1 has changed materially in the days since that research, and the single closest competitor now has meaningfully more shipped functionality than this product would have pre-build.**

1. **UpgradeGuard** (`github.com/VictorGSoutoXP/UpgradeGuard`) — **the most serious finding of this research pass.** Phase 1 (2026-09-24/25) found it "pre-MVP... README explicitly lists bytecode analysis/transaction replay/binary diffing as 'planned,' not built" (0 stars, 10 commits). **Re-checked fresh this session:** as of a push at **2026-09-24 15:40 UTC** (within the last day), it now has **working, documented `inspect` and `test-diff` commands** — `inspect` statically checks sBPF v3 `e_flags`, SIMD-0189 ELF layout, unresolved `call -1` calls, and static-syscall registration (SIMD-0178), plus a stack-overflow check via `--build-log`; `test-diff` loads a baseline and candidate binary in **two LiteSVM instances** and diffs status, return data, normalized logs, account state, and write set — i.e., the two headline mechanisms of this exact pitch, already built. Its own internal planning doc (`research.md`, VERIFIED fetched fresh) targets **the same date window (14/09–12/10/2026)**, cites the **identical 17,332-program figure** and the **identical "Agave 4.4, ~Nov 2026" claim**, and is explicitly scoped as a broader GitHub-App/SaaS/auto-PR platform with its own (unvalidated) $99-5,000/mo pricing tiers. Commit branch names (`claude/project-thread-*`, `claude/readme-and-research-*`) suggest this is also an AI-agent-assisted build, converging on the same insight through a similar process. **Confirmed, verified differentiators that still stand, checked by direct grep of UpgradeGuard's full raw README this session:** (a) `test-diff` requires a manually-authored `--fixtures fixtures.json` file — zero mentions of "signature," "getSignaturesForAddress," "recent tx," or "real transaction" anywhere in its README — it does **not** auto-fetch real recent mainnet traffic the way this product's `fetch` command does; (b) `inspect` contains **zero mentions of "0459" or "0460"** anywhere — its stack check is a narrower compile-time 4KiB-overflow warning via `cargo build-sbf` logs, not the SIMD-0459/0460 runtime stack-address-dependence semantic check this pitch covers. **Why it doesn't fully solve this, honestly:** those two gaps are real and checkable, but they are gaps in an already-functional competing tool aimed at the same market in the same contest window, not gaps in a "planned, not built" tool as Phase 1 characterized it two days ago. **This is the single biggest risk in this entire deck and should be treated as such**, not softened for pitch-video optimism.
2. **SolanaRepro** (`github.com/caiomodesti/SolanaRepro`) — unchanged since Phase 1 (last commit 2026-08-26, "prepare v0.1 review and grant package"; VERIFIED, no new commits found this session). Still explicitly MVP-scoped to "SOL transfers, classic SPL token transfers, deterministic system failures," with complex CPI, ALT reconstruction, Token-2022, and DeFi protocols explicitly listed as unsupported — the exact complex-CPI programs most at risk from SIMD-0459/0460 are the ones it cannot touch.
3. **Surfpool `profile`** (PR [#786](https://github.com/solana-foundation/surfpool/pull/786)) — still open, unmerged, last activity 2026-09-14 (VERIFIED fresh this session, unchanged). No binary-override capability; a reviewer-flagged historical-feature-state correctness bug remains unresolved. Surfpool the project is large and active (602 stars) but this specific gap is untouched.
4. **`feature-activation-verifier`** (Solana Foundation, `github.com/solana-foundation/feature-activation-verifier`) — VERIFIED fresh this session, 1 star, last pushed 2026-05-26 (no activity since Phase 1's check). Generic feature-gate pass/fail matrix, not per-program, not a replay/diff tool.
5. **sBPF decompiler toy repos** (`SpriteDay/sbpf-decompiler`, `owizdom/SBPF-3-1`) — VERIFIED unchanged this session (0 stars each, last pushed 2026-09-12 and 2026-01-06 respectively, no new activity). Generic "decompile this .so" utilities, not positioned as migration or diffing tools.
6. **Mollusk** and **Trident** — surfaced fresh this session via UpgradeGuard's own competitive-scan table (which names them as gaps it fills, not as complete solutions): Mollusk is a test-harness library (execution only, requires manual workflow composition around it, no auto-fetch/diff/lint built in); Trident is a fuzzing/regression framework with no protocol-change detection or auto-PR/replay-report generation. Neither combines fetch+replay+diff+lint.
7. **`solana-verify` / Verified Builds** — confirms build *authenticity* (does the on-chain buffer match a given source repo), not *content* diffing or runtime-behavior diffing; a different, narrower guarantee, unchanged from Phase 1's framing.

**Self-critical summary:** if forced to rank this idea's whitespace today versus at Phase 1 research time, it has dropped meaningfully — not to zero (the two confirmed gaps in UpgradeGuard are real and specific, and "real-traffic auto-fetch" plus "SIMD-0459/0460 static coverage" are legitimate, demoable differentiators), but a judge who checks both projects side by side will see real functional overlap on the headline mechanism, built by someone else, days before this pitch is finished. Any go/no-go decision on this candidate should weigh this finding heavily.
