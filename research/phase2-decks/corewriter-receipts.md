# corewriter-receipts — Pitch Deck (Candidate #1)

Track: Hyperliquid ($100k / 10 winners). Domain: async/cross-VM infra. Working name kept: **corewriter-receipts** (see naming note in §1).

---

## 1. Title + one-liner

**corewriter-receipts**
*A Rust crate + daemon that tells HyperEVM developers what their `CoreWriter` call actually did on HyperCore — because HyperEVM won't.*

Naming note: considered alternatives — `hl-receipts` (too generic, collides conceptually with exchange "receipts" terminology broadly), `corewriter-verify` (VM-02's name — reads more like a static linter/pre-flight tool than a live outcome tracer, which undersells the join-and-report mechanism that is the actual core of the product), `cw-outcome` (accurate but forgettable). **corewriter-receipts** wins because it names the exact mental model we're selling: for every `CoreWriter` call you fire, you get back a receipt — proof of what happened, the thing HyperEVM itself refuses to give you. Kept as-is.

## 2. Problem statement

**The gap, in one sentence:** A HyperEVM transaction that calls the `CoreWriter` precompile (`0x3333...3333`) reports success — `status 1`, a correctly-decoded `RawAction` event — even when the corresponding action on HyperCore (the actual L1 exchange/order-book/margin engine) is silently rejected, dropped, or never executed. No revert. No error event. No trace, anywhere a developer would naturally look.

**Evidence:**

1. **VERIFIED (fetched fresh this session, 2026-09-25):** GitHub issue [hyperliquid-dex/node#172](https://github.com/hyperliquid-dex/node/issues/172), opened 2026-09-21 by `wsim101`, **still open, still zero comments, updated_at == created_at** — i.e. four days later, unanswered by the Hyperliquid team. Verbatim from the issue body: *"CoreWriter (`0x3333...3333`) actions succeed on HyperEVM testnet (tx status 1, `RawAction` event emitted with correct data) but produce **no effect on HyperCore whatsoever** — no fills, no ledger entries, nothing. Confirmed across order placement (buy and sell) and plain token transfers."* Reporter used a freshly-created, freshly-funded account specifically to rule out account-state confounds, and tested on two separate days (2026-09-20 and 2026-09-21) with the same result.
2. **VERIFIED (fetched fresh this session):** Sister issue [hyperliquid-dex/node#171](https://github.com/hyperliquid-dex/node/issues/171), opened 2026-09-21, 02:27 UTC, describing CoreWriter spot **buy** orders never filling while sells and UI-submitted buys on the same market work fine. **Important honesty flag (new finding, not in Phase 1):** this issue was **closed by the reporter themselves 7 minutes after opening** (02:34 UTC), with **zero comments** and no visible resolution explaining why. Phase 1 (both VM-02 and H1) cited #171 as corroborating evidence without noting it was self-closed unexplained. This does not kill the core claim — #172 (the broader "no effect whatsoever" issue) remains open, unanswered, and is the stronger of the two — but #171 specifically should not be leaned on as a second independent open bug; it may have been reporter error, a duplicate, or something the reporter figured out privately. Treat #171 as **weak/withdrawn evidence** going forward.
3. **VERIFIED (fetched fresh this session):** Chainstack's HyperEVM CoreWriter developer guide states plainly: *"sendRawAction emits its log and the EVM transaction succeeds whether or not HyperCore accepts the action... If the action is malformed or the account is not set up, HyperCore drops it silently—no EVM revert, no error event"* and *"CoreWriter does not return a value to the caller... To confirm an action took effect, read HyperCore state"* (via `/info` endpoints, read precompiles at `0x0800+`, or manually watching the L1 explorer). https://docs.chainstack.com/docs/hyperliquid-corewriter
4. **VERIFIED (fetched fresh this session):** Hyperliquid's own official docs page describing the CoreWriter contract (fetched via its `.md` export) documents gas cost (~25,000 gas) and a delayed-execution quirk — order actions and vault transfers are *"delayed onchain for a few seconds"* and *"appear twice in the L1 explorer: first as an enqueuing and second as a HyperCore execution"* — but **contains no documentation of error handling or failure-detection for a rejected action.** The silent-failure behavior is confirmed by a third party (Chainstack) explaining what the first party (Hyperliquid) leaves undocumented. This is new, fresh confirmation beyond what Phase 1 had (Phase 1 only had the Chainstack quote, not a direct check of Hyperliquid's own docs).
5. **VERIFIED (fetched fresh this session):** `crates.io` search for `corewriter` returns **0 results**. A search for `hyperliquid` returns 10 crates (SDKs, backtesting, trading bots, an MCP server) — none is an outcome-correlation tool.
6. **VERIFIED (fetched fresh this session):** `hyperliquid-dex/node`'s own README documents the raw building blocks that would make correlation possible but confirms nobody has wired them together: the `--write-system-and-core-writer-actions` flag writes output to `~/hl/data/system_and_core_writer_actions/hourly/{date}/{hour}`, described as *"indexed by HyperEVM tx hash and a unique system nonce."* Separately, `--replica-cmds-style actions-and-responses` writes both an action and its response to `~/hl/data/replica_cmds/{start_time}/{date}/{height}`, and `--write-order-statuses` streams every order status change to `~/hl/data/node_order_statuses/hourly/{date}/{hour}`. The correlation key (tx hash + nonce) is already emitted by the node. Nobody has built the join.
7. **VERIFIED (fetched fresh this session):** Hyperliquid's official "L1 data schemas" doc page (`for-developers/nodes/l1-data-schemas.md`) documents schemas for **order statuses**, trades, raw book diffs, and misc events — but has **no documented schema at all** for `system_and_core_writer_actions`, and only names the `replica_cmds` file path without documenting its `actions-and-responses` field format. This directly confirms VM-02's claim that this specific output is undocumented in the public gitbook — verified firsthand this session, not just inherited.

**Who exactly hits this, how many, where they'd find this product:** Rust/Solidity developers building HyperEVM contracts or off-chain bots that call `CoreWriter` to act on HyperCore — HIP-3 market builders, lending-market and vault protocols that rebalance or hedge via CoreWriter, LST issuers, market-making bots. Phase 1's ecosystem scan (GitHub search across three independent query patterns) found roughly **10-20 active CoreWriter-integrated repos** as of Sept 2026 (`hyper-evm-lib` consumers, `hypervault`, `native-markets/hyperevm-tools`, `emo-eth/hyperevm-tools`, etc.) — this session's fresh search for `corewriter` and `hyperevm hypercore` found the same population again (9 + 17 repos respectively, heavy overlap, all libraries/playgrounds/indexers, none an outcome tracker). This is a small, nameable, growing population, not a mass market — consistent with the brief's "niche everybody knows exists but nobody big will serve" strategy. They gather on the `hyperliquid-dex/node` GitHub issue tracker (where #172 lives) and the Hyperliquid developer Discord (`#hyperevm-dev`).

**Honest risk flagged here, not smoothed over:** the population is small (dozens, not thousands) and one of the two headline GitHub issues weakened under fresh scrutiny (self-closed, unexplained). The core claim survives on #172 plus the Chainstack doc plus the two first-party docs gaps (CoreWriter error handling undocumented; schema undocumented) — four independent, verified confirmations of the same structural gap — but the "two fresh open bugs" framing from Phase 1 should be revised to "one fresh open bug, corroborated by first-party doc gaps and a fire-and-forget-by-design architecture."

## 3. What we are

**Ships as:**
- **`corewriter-receipts`** — a Rust library crate exposing an async API like `await_outcome(tx_hash: H256) -> Outcome` that any HyperEVM contract's off-chain bot, indexer, or test harness can embed directly.
- **`corewriter-receipts-daemon`** — a small standalone binary (same core engine, wrapped in a long-running process) for teams that don't want to embed a Rust dependency into their own service. Exposes a local HTTP/webhook interface: register a tx hash (or a watched address), get a push notification (webhook POST, or a simple SSE/streaming endpoint) the moment an outcome resolves.
- A CLI (`corewriter-receipts watch <tx_hash>`) for interactive debugging — the "paste a tx hash, see what actually happened" workflow that #172's reporter needed and didn't have.

**Core technical mechanism — be specific:**

1. **Inputs (two independently-sourced streams, joined by a correlation key that already exists in hl-node's own output):**
   - **EVM side:** subscribe to `RawAction` events emitted by the `CoreWriter` precompile (`0x3333...3333`) on a HyperEVM RPC/WebSocket endpoint. Decode the action payload (order type, transfer type, etc.) per the documented action-ID set.
   - **Core side:** tail a non-validator `hl-node`'s own output files: `~/hl/data/system_and_core_writer_actions/hourly/{date}/{hour}` (indexed by **HyperEVM tx hash + a unique system nonce** — confirmed by hl-node's own README, this is the exact join key), `~/hl/data/replica_cmds/{start_time}/{date}/{height}` run with `--replica-cmds-style actions-and-responses` (captures the action *and its response*, i.e. accept/reject), and `~/hl/data/node_order_statuses/hourly/{date}/{hour}` (per-order status stream, which per the official L1-data-schemas page has a documented `status` field — this is where rejection reasons like `tickRejected`/`minTradeNtlRejected`/margin failures surface).
   - Where running your own node is impractical, the daemon falls back to polling HyperCore's public `/info` endpoints (`orderStatus`, `clearinghouseState`) — slower and less complete, but zero-infra.
2. **Correlation:** join by (HyperEVM tx hash, system nonce) when reading node output directly — an exact key match, no fuzzy heuristics needed, because hl-node already emits this pairing. When falling back to `/info` polling, join by (user address, action type, nonce/timing window) as a secondary heuristic, and be honest in the output about which correlation method produced the result (exact-key vs. best-effort) — this is a place a demo or judge could probe, so we don't overclaim polling-mode precision.
3. **Timing:** Hyperliquid's own docs confirm order actions and vault transfers are delayed "a few seconds" and execute in two visible stages (enqueue, then execution) — the join window has to span that delay, not assume same-block execution. This is a concrete, first-party-confirmed constraint the tool has to handle correctly, and a good thing to show explicitly in the demo (see §4).
4. **Output:** a structured `Outcome` — `Success { fill/transfer details }` or `Rejected { reason }` (surfacing whatever reason string the node's order-status stream reports) or `Unresolved { still pending }` — exposed via the crate API, the CLI, and the daemon's webhook.
5. **Folded-in VM-02 idea (pre-flight footgun check):** before submission, optionally check the one documented, recurring footgun class — account-not-yet-initialized-on-Core-in-the-same-block — via a light read-precompile check, and warn the caller *before* they burn gas on a call that's structurally guaranteed to be dropped. This is a bonus, not the core value prop; the core value prop is the outcome join.

**Why this is a pure-Rust artifact, not a web dApp:** the entire product is infrastructure that sits between two async event streams and speaks their native formats (EVM JSON-RPC/WebSocket logs on one side, hl-node's raw file-based output format on the other) and re-exposes a typed API. There is no end-user-facing UI to build a dApp around — the "customer" is a developer's own bot, CI pipeline, or monitoring stack, which is exactly the shape of thing that should be a library/daemon a Rust program links against or a CLI a terminal-based workflow calls, not a hosted website. Rust's async ecosystem (tokio, and typed decoding of two different binary/structured-log formats) is a genuine fit, not a stylistic choice.

**Who's building this:** solo builder, hackathon submission for Colosseum's Crypto World's Fair.

## 4. Tech demo (3-minute plan, minute-by-minute)

**Goal:** prove the tool catches, live, the exact real bug from issue #172 — reproduce the reported behavior, then show `corewriter-receipts` diagnosing it in seconds where the actual GitHub reporter spent an unanswered multi-day investigation.

- **0:00–0:30 — Set the stakes.** Screen: the actual open GitHub issue #172 (hyperliquid-dex/node), scrolled to the "no effect on HyperCore whatsoever" line. Voiceover: this is a real, currently-unanswered bug report from four days ago; here's what a developer sees today with zero tooling.
- **0:30–1:00 — Fire two CoreWriter transactions on HyperEVM testnet, side by side in a terminal.** Transaction A: a well-formed spot limit order (control case, should fill). Transaction B: a deliberately malformed one — reproducing the reported failure mode, e.g. a tick-misaligned price or an order routed to an account with insufficient margin. Show both transactions return `status 1` on HyperEVM in a block explorer or `eth_getTransactionReceipt` output — visually identical successes.
- **1:00–1:30 — Show the void.** Pull up the HyperCore side (the L1 explorer / `/info` `orderStatus` for both). Transaction A shows a fill. Transaction B shows... nothing. No order, no error, no trace — this is the exact gap from the issue, reproduced live, not just quoted.
- **1:30–2:15 — Run `corewriter-receipts watch <txB_hash>`.** Show the daemon's terminal output resolving within seconds to a structured outcome: `Rejected { reason: ... }` (or "Unresolved" with a clear next-step if the underlying rejection-reason field isn't populated in this build — be honest on camera if the MVP's reason-decoding is partial). Immediately follow with `corewriter-receipts watch <txA_hash>` resolving to `Success { fill details }` — the control case, proving the tool isn't just reporting "always failed."
- **2:15–2:45 — Show the webhook path.** A second terminal running the daemon with a webhook registered; fire a third transaction live; the webhook fires a push notification the instant HyperCore resolves it — demonstrating the "team doesn't have to poll, gets alerted" production use case from the business model.
- **2:45–3:00 — Close on the gap this fills.** One slide: "Today: silent failure, unanswered GitHub issue, manual `/info` polling. With corewriter-receipts: a structured answer in seconds." Show the crate on crates.io (or the repo) and the one-liner.

**Demo risk to flag honestly:** reproducing a *specific* rejection reliably on testnet (vs. just "no effect") may take some testnet fiddling in the actual 14-day build — the issue reporter tried several deliberate-failure scenarios (bad tick, insufficient margin, fresh wallet) before landing on ones that reproduced consistently. Budget real testnet-experimentation time before the demo, not just build time.

## 5. Business model

**Who pays, how, and why this maps to "viable business":**

- **Free tier (adoption engine):** the `corewriter-receipts` crate and CLI, self-hosted, OSS (MIT/Apache-2.0) — free for solo devs and small teams who run their own hl-node or are fine with `/info`-polling mode. This is also what the Open-source judging criterion rewards directly.
- **Paid tier (the actual business):** a hosted correlation/alerting service — teams that don't want to run their own Hyperliquid node point their CoreWriter-calling contracts/bots at a hosted endpoint and get webhook alerts when actions silently fail, without touching node infra themselves. This mirrors an established, understood business shape in this exact niche: Phase 1 identified this as analogous to Chainstack's dedicated-RPC-as-a-service model for HIP-3 deployers (Chainstack sells managed Hyperliquid infra access; this sells managed *outcome visibility* on top of CoreWriter specifically), and more broadly to Sentry/Tenderly-Alerts-style "pay per project to get alerted when something silently breaks" monitoring products.
- **Realistic pricing:** per-project monthly tiers (e.g., a handful of watched contracts free, then priced per additional contract/volume-of-actions-monitored) — consistent with how Tenderly Alerts and similar devtool-monitoring products price. Given the small (dozens) named population, near-term revenue is modest — this is a genuine, honestly-small business, not a "TAM slide" story. The realistic pitch is: a real, if narrow, recurring-revenue SaaS wrapped around free OSS adoption, not a venture-scale platform play on its own — though it composes naturally into a broader "HyperEVM observability" product if the ecosystem grows (which several Phase 1 scouts flagged as the natural expansion path).
- **Channel:** Hyperliquid developer Discord (`#hyperevm-dev`), the same GitHub issue tracker where the underlying bug lives (the tool's own README/launch post can literally link back to #172 as the motivating bug it fixes), and Hyperliquid ecosystem grant/builder programs.

## 7. Track fit & judging-criteria mapping

- **Functionality:** A working Rust crate + CLI + daemon that decodes real HyperEVM logs, tails real hl-node output files (or polls real `/info` endpoints), and joins them on a verified, first-party-documented correlation key (tx hash + system nonce) — not a mockup. Demo proves it resolves a real reproduced failure in seconds.
- **Potential Impact:** Narrow but real and structurally permanent — CoreWriter's fire-and-forget design is architectural (a breaking consensus change would be needed to fix it protocol-side per Phase 1's analysis), so this gap doesn't close on its own as Hyperliquid grows; every new CoreWriter-integrated protocol (HIP-3 markets, vaults, LST issuers) inherits the exact same blind spot. Impact is bounded by population size (dozens today), which we state plainly rather than inflate.
- **Novelty:** Confirmed zero competing crates (`corewriter` returns 0 hits on crates.io) and zero competing outcome-correlation tools among 9+17 adjacent GitHub repos checked fresh this session — all are either Solidity call libraries, one-directional indexers (envio's indexer explicitly out-of-scope for outcomes; d4mr/coredrain does the *opposite* direction, HyperCore→EVM), or local Foundry simulators (hyper-evm-lib), not live outcome trackers.
- **UX:** Directly targets the judging language "how well does this... create great UX for downstream users" — the downstream users here are developers integrating CoreWriter, and the entire product *is* a UX fix for a documented, first-party-confirmed dead end (Hyperliquid's own docs are silent on failure detection; this tool is the missing feedback loop).
- **Open-source:** Ships as an OSS crate on crates.io by design (part of the go-to-market, not just a compliance checkbox); composes with the existing HyperEVM tooling ecosystem (hyper-evm-lib, hyperevm-tools) as a complementary layer rather than a replacement — those tools help you *call* CoreWriter, this tool tells you *what happened*.
- **Business Plan:** A modest but real, precedented business model (Chainstack/Tenderly-Alerts-shaped), honestly scoped to a small near-term market with a credible expansion path (broader HyperEVM observability) if the ecosystem grows — see §5's honesty flag on TAM size.
