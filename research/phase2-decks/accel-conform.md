# accel-conform — zkVM Accelerator Conformance & Differential Test Kit

*Deck author's note on the name: "accel-conform" is kept as the working name — it is accurate and greppable (accelerator + conformance). No sharper alternative found in this pass justifies a rename; "zkevm-precompile-conform" was considered but is less accurate since `zkvm_accelerators.h` covers non-EVM-precompile functions too (e.g. `secp256r1_verify`, KZG). Keeping "accel-conform."*

---

## 1. Title + one-liner

**accel-conform** — a pure-Rust crate + CLI that catches soundness-breaking bugs in zkVM cryptographic accelerators (ecrecover, BLS12-381, modexp, KZG, etc.) before they reach a mainnet prover, using known-answer test vectors and live cross-vendor differential testing across SP1, OpenVM, and beyond.

---

## 2. Problem statement

**The interface.** The Ethereum Foundation's `eth-act/zkevm-standards` project defines `zkvm_accelerators.h`, a shared C ABI so zkVM guest programs can call one portable interface for cryptographic primitives (keccak256, secp256k1 verify/ecrecover, sha256, ripemd160, modexp, BN254 ops, blake2f, KZG point-eval, BLS12-381 G1/G2/pairing/map-to-curve, secp256r1 verify) instead of each guest re-implementing crypto in slow interpreted RISC-V.
- VERIFIED (fetched this session, 2026-09-25): current header defines **19 accelerator functions** across 8 primitive families. https://github.com/eth-act/zkevm-standards/blob/main/standards/c-interface-accelerators/zkvm_accelerators.h — content is materially unchanged from Phase 1's ~17-function count (Phase 1 undercounted slightly; not a substantive change).

**Two real, disclosed, soundness-relevant bugs exist in this layer** — this is the evidentiary core of the pitch:

1. **SP1 — BLS12-381 encoding bug.** `succinctlabs/sp1#2881` (opened 2026-07-13, still **open** as of this fetch): SP1's `zkvm_bls12_381_fp2` accelerator encodes Fp2 as `c1 || c0` and infinity as a `0x40` flag byte, while EIP-2537 (which the header's own docs reference) specifies `c0 || c1` and an all-zero infinity encoding. "Anyone who passes in EIP-2537 bytes gets wrong results with no error." — VERIFIED, https://github.com/succinctlabs/sp1/issues/2881.
   - **Update since Phase 1, materially relevant:** a fix, PR `succinctlabs/sp1#2865`, has existed since **2026-07-02** — three weeks *before* the bug report that spawned the discussion thread — and is still **open, unmerged, unreviewed** as of this fetch (last activity 2026-07-06; the bug thread's own participants had to point the fix author (@tamirhemo) at it on 2026-08-09, over a month after it was filed). VERIFIED, https://github.com/succinctlabs/sp1/pull/2865. This is stronger evidence for the "no one owns cross-vendor conformance" structural claim than Phase 1 had: a known, ready fix has sat unreviewed for ~2.5 months.
   - The correct encoding is itself contested: `eth-act/zkevm-standards#35` (open) notes ZisK follows EIP-2537 (`c0||c1`, all-zero infinity) while SP1 does the opposite, and states plainly: "the canonical encoding is currently un(der)-specified." VERIFIED, https://github.com/eth-act/zkevm-standards/issues/35.

2. **OpenVM — secp256k1 ecrecover wrong-key bug — CONTESTED, weakened since Phase 1.** `openvm-org/openvm#3147` (opened 2026-09-03, still open): reporter's known-answer test shows `zkvm_secp256k1_ecrecover` returning `ZKVM_EOK` with a **wrong recovered public key**, with two independent malleability-variant vectors both failing silently. VERIFIED, https://github.com/openvm-org/openvm/issues/3147.
   - **New finding this session, must be stated plainly per research rules:** the most recent comment on the issue (2026-09-04, from an apparent OpenVM team member, "we were unable to reproduce this" earlier in the thread) reads: *"both the bugs don't seem to reproduce on a native x86 machine and on qemu and it works on rosetta with `-mno-bmi2` or `-march=x86-64`. this seems like a bug in rosetta related to bit manipulation instruction support."* This suggests the failure may be an artifact of the **reporter's own Apple-Silicon-via-Rosetta test environment** mis-emulating BMI2 bit-manipulation instructions in the native comparison path, not a genuine OpenVM accelerator defect. The issue has had **zero further activity in three weeks** (as of 2026-09-25) — neither confirmed as a real accelerator bug nor closed as a test-environment artifact. **This bug is now contested, not confirmed**, and the deck below flags it as such everywhere it's used; do not present it to judges as flatly "confirmed" without this caveat.

**The structural gap that lets bugs like this ship**, and the state of it as of this session — **also materially updated since Phase 1**:
- `eth-act/zkevm-standards#16` ("EF to provide reference implementation... for cross-checking with vendor implementations," open since 2026-03-11) was, per Phase 1, dormant with zero comments. **It is no longer dormant.** In the 72 hours immediately before this research (2026-09-22 to 2026-09-24), eth-act maintainers `jsign` and `han0110` held a live discussion on this exact issue, disclosing that **`eth-act/ere` already merged, on 2026-08-25 (`ere` PR #413), a known-answer test-vector corpus (extracted from `execution-specs@tests-zkevm@v0.8.2`) plus a guest-program harness that runs every vector through the real accelerator on OpenVM, SP1, and ZisK and checks the result against a recorded reference outcome** — i.e., components (1) and (2) of this product's spec, already built, a month before Phase 1's research pass (which checked zkvmBlast but not `ere` itself for this). VERIFIED, https://github.com/eth-act/zkevm-standards/issues/16#issuecomment (comments dated 2026-09-22/23/24) and https://github.com/eth-act/ere/pull/413 (merged 2026-08-25). **See section 8 for what this does and does not close.**
- Confirmed still true, VERIFIED (re-fetched): `eth-act/zkevm-test-monitor`'s live dashboard (https://eth-act.github.io/zkevm-test-monitor/) is pure RISC-V ISA compliance testing (ACT4 framework) — grepped the rendered dashboard HTML for "accelerator/precompile/conformance," zero matches. The maintainers' 2026-09-23/24 discussion explicitly treats folding accelerator-conformance results into this dashboard as an **undecided, unowned future step** ("wondering if this should be still done in Ere vs the tracker repo... no strong opinion" — han0110, 2026-09-24). Nothing is shipped publicly yet.
- Confirmed still true, VERIFIED (re-fetched): `zkvmBlast` (zksecurity) README, re-grepped for "accelerat|zkvm_|precompile" — the only hits are about its `--with-precompiles` flag, which patches guest crates for **performance comparison only**, with zero mention of the standardized C accelerator interface or known-answer correctness checking. https://github.com/zksecurity/zkvmblast/blob/main/README.md

**Who exactly this affects — named, reachable, in 2026:** core engineers on the RISC-V zkVM teams implementing `zkvm_accelerators.h` — **SP1/Succinct, RISC Zero, OpenVM, ZisK, Airbender, Jolt, Pico** (6–8 named teams, all building in public on GitHub) — plus any team building an EVM-equivalent guest program (rollup provers, stateless-validation clients) that links these accelerators and inherits their correctness silently. `ere` itself — the harness this product depends on — currently only compiles/proves for **3 of those 8 teams (OpenVM, SP1, ZisK)**, VERIFIED from `ere`'s own README supported-zkVM list (https://github.com/eth-act/ere/blob/master/README.md) — a real, previously-unflagged feasibility constraint discussed in section 8.

**Why the cost is real, not annoyance:** a wrong-but-`ZKVM_EOK` accelerator result means a guest computes an incorrect state transition (wrong ECDSA sender, wrong pairing check, wrong KZG opening) and the zkVM still emits a **valid cryptographic proof of that wrong computation**. Anything settling on the strength of that proof — a rollup, a stateless-validation client, an EVM-equivalence claim — accepts a fabricated result as ground truth. This is a stolen/fabricated-money-class failure, not a debugging inconvenience.

## 3. What we are

**The product**, restated precisely against what's already public (see section 8 for exact delta):

1. **Known-answer vector corpus** — sourced from existing spec test vectors (EIP-2537 for BLS12-381, EIP-198 for modexp, standard secp256k1/BN254 vectors, RFC vectors for hashes) for every function in `zkvm_accelerators.h`, kept in a versioned, auto-refreshable format (unlike the current `ere` fixtures, which are a one-time extraction from `execution-specs@tests-zkevm@v0.8.2` with no update workflow — v0.8.4 already exists and isn't pulled in, per the maintainers' own 2026-09-24 discussion).
2. **A guest-program harness built on `ere`** (the eth-act unified zkVM interface — chosen specifically to avoid reinventing per-zkVM compile/link/run plumbing that `ere` already solves) that runs each vector through the real accelerator on each target zkVM and checks **both status code and output** against the known answer — explicitly designed to catch the exact "`ZKVM_EOK` but wrong" bug class both disclosed bugs fall into.
3. **A differential mode** that cross-checks all covered zkVMs against each other *and* against a pure-Rust reference implementation for the same primitive, computed independently at test time rather than baked into a fixture — this is the piece that would have surfaced the SP1/ZisK BLS12-381 encoding disagreement (`#35`) as a live three-way mismatch report ("SP1 says X, ZisK says Y, EIP-2537 reference says Z") instead of requiring a human to notice it by manual inspection, which is how it was actually found.

**Why pure Rust:** every zkVM guest toolchain here targets `riscv{32,64}im*` via Rust (SP1/OpenVM/ZisK guest SDKs are Rust-only or Rust-first), `ere`'s host/guest split is a Rust trait system, and the reference implementations being cross-checked against (arkworks, k256, RustCrypto hashes) are the same pure-Rust crates the wider ecosystem already trusts for EVM precompile correctness — there is no reason to introduce a second-language boundary anywhere in this pipeline.

**Who's building this:** one solo Rust engineer, for the duration of the hackathon build window.

## 4. Tech demo (3 minutes)

- **0:00–0:20 — Setup.** One slide: "zkVM accelerators are correctness-critical and untested across vendors — here are two real, disclosed bugs that shipped anyway." Show the two GitHub issue titles and dates on screen.
- **0:20–1:10 — Run 1 (SP1, BLS12-381).** Run `accel-conform check --zkvm sp1 --accelerator bls12_381_fp2_to_g2` live against a small guest binary. Feed it an EIP-2537-encoded infinity-point vector. Show it complete in seconds with a **FAIL: expected [EIP-2537 all-zero], got [SP1 0x40-flag encoding]** report, citing `sp1#2881`/`#2865` on screen as "this is issue #2881, still unmerged as of today."
- **1:10–2:00 — Run 2 (OpenVM, ecrecover) — presented honestly as contested.** Run the same tool against OpenVM with the known-answer vector from `openvm#3147`. Say explicitly in the narration: *"This is a real, disclosed report against OpenVM's preview build. As of this week, OpenVM's own team hasn't confirmed whether it's an accelerator bug or an artifact of the reporter's test environment — that ambiguity is itself the point: without a standing, reproducible conformance harness like this one running in CI on a fixed reference environment, nobody can tell the difference quickly."* This reframes the contested bug as supporting evidence for the product rather than overclaiming it.
- **2:00–2:40 — Differential mode.** Run `accel-conform diff --accelerator bls12_381_fp2_to_g2 --zkvms sp1,zisk` and show the three-way table (SP1 / ZisK / pure-Rust reference) surfacing the live encoding disagreement in one command — tie directly back to `zkevm-standards#35`'s open "encoding is currently un(der)-specified" line.
- **2:40–3:00 — Close.** One line: "This tool would have caught both of these before they shipped — and the standards body itself has an issue open since March asking for exactly this."

## 5. Business model

- **Core: open-source public good.** The known-answer corpus, `ere`-based harness, and differential-mode CLI ship free, MIT/Apache-2.0, as infrastructure any zkVM team can run in their own CI — this is the version that's eligible for the hackathon's own Public Goods Award ($5k) and is the right default given the target users are the zkVM teams themselves, who need to *adopt* it, not be sold to.
- **Paid layer 1 — conformance certification / CI badge.** A hosted, continuously-run dashboard (the exact public artifact eth-act's own maintainers are, as of this week, debating whether to build internally and haven't shipped — see section 8) that zkVM teams and rollups can point to and embed a badge from ("SP1 v6.x: 19/19 accelerators conformant as of 2026-09-25") to credibly advertise correctness to *their* downstream users (rollups choosing a proving backend, auditors scoping a review). Realistic pricing: modest recurring fee ($500–2,000/mo) per zkVM team/rollup for a badge kept current against their release cadence — priced like a compliance-badge SaaS (comparable in spirit to how RISC-V's ACT4 compliance testing became a paid-adjacent service for vendors wanting a compliance mark), not enterprise-security-tool pricing, because the buyer base is ~6-8 teams total.
- **Paid layer 2 — CI integration consulting.** One-time or retainer engagements helping a specific zkVM team wire the differential harness into their own release pipeline (mapping their internal accelerator-call conventions into the vector corpus format) — a natural extension of the same expertise, priced per-engagement.
- **Applying the 4-point filter explicitly:**
  1. *Named, reachable users:* the 6-8 zkVM teams are literally named above, building in public, reachable on GitHub/Discord — the most concretely-named user population of any candidate reviewed in this research pass.
  2. *Real cost, not annoyance:* the cost avoided is a **soundness bug** — a fabricated or incorrect state transition accepted as a valid, verified proof. For a rollup or stateless-validation client relying on that zkVM, this is equivalent to accepting fabricated or stolen funds as canonical. This is categorically different from a debugging-hours cost (contrast: the rejected `corewriter-receipts` candidate, dropped from this research precisely because its cost was DIY-able debugging time, not money at stake).
  3. *Structural, not circumstantial neglect:* each zkVM team tests its own accelerator in isolation — that's mechanically why both bugs shipped past internal review; no single vendor has a competitive incentive to fund a *cross-vendor* conformance suite that could publicly rank them against competitors, and the standards body itself (a specification-writing body, not a test-infra shop) has had a direct, unaddressed ask for this sitting open since March 2026. This is why a zkVM team or rollup would fund/pay for it: it's a public good no single participant is structurally incentivized to build alone, but every participant benefits from someone building it, and the entity with the biggest incentive to pay (a rollup betting billions on one zkVM's soundness) is not the entity capable of building it (that's the zkVM team, which has the opposite incentive — not to publicly find its own bugs first).

## 7. Track fit & judging-criteria mapping

**Track:** Ethereum L1 ($25k / 5 winners) — zkEVM/stateless-validation correctness infrastructure sits squarely in L1 execution-layer roadmap territory (EIP-2537, EIP-198, precompile semantics all being actively re-specified for stateless clients and zkEVMs).

- **Honest note on track strength, per instruction:** ESP's own wishlist/RFP page for concrete funded asks is, as of this research pass, effectively empty compared to the more concrete, dollar-scoped asks visible on the Solana/Zcash tracks (this echoes the framing already used for this candidate's siblings in this research pass — no fresh contradicting evidence found this session; not re-verified live in this pass, carried as **INHERITED** from earlier research). This makes the track-fit case for L1 less externally-anchored than for a track with a live named RFP.
- **Does the pitch still stand without that anchor?** Yes, on its own evidence: two real, disclosed accelerator-layer issues (one confirmed live-unresolved with an unmerged fix, one contested-but-unresolved) and a *specification body's own unaddressed 6-month-old ask* for exactly this tool are independent of whether ESP currently has a funded RFP for it — the judging criteria below are evaluated on the artifact and evidence, not on the existence of a wishlist line item.

| **Potential Impact** | TAM is small in headcount (6-8 teams) but each is the trust root for potentially billions in value settled on their proofs — impact is concentrated and structural, not broad-but-shallow; a caught soundness bug has outsized downstream impact versus its narrow user count. |

## 8. Competitive scan (for the verifier) — harshest-critic pass

This section is the most important update from this research session. Ranked by how much they overlap with the actual product spec, most-overlapping first.

1. **`eth-act/ere` PR #413 (merged 2026-08-25) — closest thing to a direct precursor, found fresh this session.** https://github.com/eth-act/ere/pull/413 ; harness code: https://github.com/eth-act/ere/blob/master/crates/util/test/src/program/zkvm_interface.rs ; fixtures: https://github.com/eth-act/ere/tree/master/tests/fixtures/zkvm_interface
   - **What it already does:** ships a `Vectors`/`Vector` type with one known-answer test case per accelerator call (`inputs` + recorded `Outcome{status, output}`), extracted from real `revm::precompile::Crypto` calls recorded during `execution-specs@tests-zkevm@v0.8.2` block execution, and a guest harness that runs every vector on-device and asserts the accelerator's output matches the recorded outcome — for **OpenVM, SP1, and ZisK**. This is components (1) and (2) of the accel-conform spec, already built, a month before this hackathon's contest period even opened (2026-09-14).
   - **Why it doesn't fully solve this / what's still missing:** (a) covers only 3 of the 8 named zkVM teams — RISC Zero, Airbender, Jolt, Pico have zero accelerator-conformance coverage anywhere, in `ere` or elsewhere; (b) the vector corpus is a one-time extraction with no update workflow (execution-specs is already one release ahead, v0.8.4 vs the pinned v0.8.2, and updating it is an open, unowned discussion item as of 2026-09-24); (c) it checks each zkVM against one fixed recorded reference value, not a live n-way differential across zkVMs — it cannot by itself surface a "SP1 says X, ZisK says Y" disagreement the way a true differential mode would, which matters precisely because the BLS12-381 encoding convention itself is disputed (`#35`); (d) it is internal EF/eth-act tooling with no public certification/badge/dashboard layer, no business model, and no framing as a standalone product a rollup could point to.
   - **Bottom line:** this materially narrows accel-conform's novelty claim versus how Phase 1 scored it (Phase 1 checked zkvmBlast for this and found nothing; it did not check `ere`'s own test suite, which is the actual precursor). It does not eliminate the idea — the remaining gap (5/8 teams, continuous updates, true differential mode, public certification product) is real — but a verifier should weight "Whitespace" measurably lower than Phase 1's 5/5.

2. **`zkvmBlast`** (zksecurity) — https://github.com/zksecurity/zkvmblast — re-confirmed this session (README re-fetched, re-grepped): ISA-level differential *instruction execution* fuzzing against a Spike reference across SP1/RISC0/OpenVM/Pico/ZisK/Airbender, with a `--with-precompiles` flag that patches guest crates purely for **performance** comparison, not correctness checking. Zero mention of `zkvm_accelerators.h` or known-answer accelerator testing. Confirmed unchanged from Phase 1's finding. Does not solve this.

3. **`eth-act/zkevm-test-monitor`** — https://github.com/eth-act/zkevm-test-monitor, dashboard https://eth-act.github.io/zkevm-test-monitor/ — re-confirmed this session (README + live dashboard HTML re-fetched, re-grepped for "accelerator/precompile/conformance": zero matches): pure RISC-V ISA compliance testing via the ACT4 framework across SP1/Jolt/OpenVM/ZisK/Airbender. Explicitly *not* accelerator/precompile correctness — confirmed unchanged from Phase 1, but now also confirmed to be the repo the eth-act team is, as of 2026-09-23/24, actively discussing as the *eventual* home for accelerator-conformance results ("automating most of the compliance tests... READINESS.md dashboard" — han0110). Not built yet; a live, undecided competitive threat to watch, not a shipped one.

4. **Arguzz** (academic, USENIX Security 2026) — repo https://github.com/Rigorous-Software-Engineering/arguzz — re-confirmed this session (README re-fetched, re-grepped for "accelerat/precompile": zero matches): metamorphic + fault-injection fuzzing at the **constraint-system/circuit level** across Jolt, NexusVM, OpenVM, Pico, RiscZero, SP1 — finds soundness bugs in arbitrary guest-code proving (e.g., instruction-level miscompilation), a different layer from "does the standardized accelerator ABI compute the right cryptographic answer." Confirmed unchanged from Phase 1. Does not solve this.

5. **`succinctlabs/sp1#2865`** — not a competitor, but worth noting as adjacent existing work: this is a *point fix* for one accelerator family on one zkVM, not a suite; its own ~2.5-month unreviewed backlog is itself evidence for the structural-neglect argument in section 5.

**Harshest-critic summary:** the single biggest risk to this candidate, found fresh this session, is that the *mechanism* half of the product (known-answer vectors + `ere`-based cross-zkVM guest harness) already exists, built by the same team whose repo this product would depend on, merged a month before the hackathon opened. The defensible remaining pitch is narrower than Phase 1 scored it: expand coverage to the 5 zkVM teams `ere` doesn't reach, keep the corpus current against spec releases, add a genuine live differential mode (not just checking against one baked-in answer), and — most importantly for "Business Plan" — build the public-facing certification/dashboard product that eth-act's own maintainers are debating building internally but have explicitly not committed to or shipped as of this session (2026-09-24 discussion, no decision recorded).
